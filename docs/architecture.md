# 架构

## 一条主线

HeavyHeader 的架构只有一条设计原则，其他一切都是它的推论：

> **不自己解析 C++。**

工具向真实编译器提问，读取它的回答。因此分析结果在构造上是精确的——不存在一个会出细微
差错的手写预处理器。一个手写解析器在遇到模板元编程、条件编译、宏拼接时会静默给出错误
答案，而这种错误比崩溃危险得多。

## 分层

```
┌─────────────────────────────────────────────────────────────┐
│  cli.py            四个命令的薄壳，只做参数解析和输出        │
├─────────────────────────────────────────────────────────────┤
│  scanner.py        编排：发现 TU → 并行编译 → 汇总统计       │
│  verify.py         实测：注释掉 include → 重编译 → 计时      │
│  baseline.py       基线、对比、CI 门禁判定                   │
├─────────────────────────────────────────────────────────────┤
│  attrib/           纯函数：依赖图、独占闭包、使用启发式       │
│  parse/            纯函数：编译器输出 → 数据模型             │
├─────────────────────────────────────────────────────────────┤
│  drivers/base.py  唯一碰子进程的一层                         │
└─────────────────────────────────────────────────────────────┘
```

**关键性质：`attrib/` 和 `parse/` 是纯函数，不碰编译器、不碰文件系统、不碰网络。**
这让核心逻辑可以被彻底单元测试——`tests/test_attribution.py` 的全部用例都不需要
安装任何编译器。

## 几个刻意的设计选择

### 1. 一次编译拿三样数据

`-H`、`-ftime-report`、`-fsyntax-only` 在同一次调用里全部生效。分两次调用会让扫描耗时
翻倍，更糟的是两次之间头文件若变化，两边数据会矛盾。

### 2. 用 `-fsyntax-only` 而不是完整编译

默认不写目标文件、不做代码生成——我们测量的是头文件的影响，而头文件主要作用在预处理和
解析阶段。需要代码生成阶段时用 `--full-compile`，文档里说明代价。

### 3. `-M` 的依赖清单从 include 树重建

`-M` 隐含 `-E`（只预处理），无法和一次真实编译并存。而 `-H` 给出的树是 `-M` 的超集，
所以直接从中重建扁平清单——信息没丢，调用少一次。

### 4. 编译器路径归一化

Windows 上编译器输出的路径可能是 `C:/mingw64/...`（正斜杠）而项目根是 `C:\proj`。
不归一化的话，`Path.relative_to()` 会静默失败，项目头文件会被误判为第三方，
于是「成本热点」表变成空的——一个看起来像「没有数据」实际是「分类错了」的 bug。
所有路径在进入数据模型前都经过 `_normalise()`。

### 5. 迭代而非递归地算闭包

真实项目的 include 链可以深达数千层，Python 默认递归上限 1000。
`closure_of()` 用显式栈。测试用 5000 层的链子锁定这个性质。

### 6. `compile_commands.json` 优先

有它就用它的 flags。同一份代码在不同 flags 下的数字没有可比性——
`-DNDEBUG` 改变的是代码路径，不是噪声。

## 报告是自包含单文件

HTML 报告不引 CDN、不引框架、图表是手写内联 SVG。这不是技术偏好，是需求：
报告要贴进 PR、要发给别人、要在没网的机器上打开。一个在这些场景下显示白页的报告
毫无价值。

数据量级（几十个头文件、几十个历史点）也远不够撑起一个图表库的开销。

## 测试策略

| 层次 | 位置 | 需要编译器？ |
|---|---|---|
| 解析器 | `tests/test_parsers.py` | 否，用真实编译器输出做样本 |
| 归因引擎 | `tests/test_attribution.py` | 否，构造数据模型 |
| 门禁与序列化 | `tests/test_gate.py` | 否 |
| 端到端 | `.github/workflows/ci.yml` 的 `self-scan` | 是 |

样本不是编的：`tests/test_parsers.py` 里的 `-H` 和 `-ftime-report` 输出是从 GCC 16.2
(MinGW) 真实运行复制的。这也意味着换编译器版本时这些测试会最先报警。
