# 候选识别精度：差距、改动、对照（2026-10-19）

本轮目标不是加功能，而是把「**找到并定位优化点**」这件事的精度量化、然后改对。
所有真值来自编译器，不来自人工判断。

## 0. 真值怎么来的

两条独立真值，缺一不可：

| 真值 | 怎么测 | 为什么必须 |
|---|---|---|
| 编得过吗 | 注释掉那一行，用编译数据库里的原命令真编一次 | 编不过的候选对使用者没有价值 |
| 真少解析了吗 | 同一次编译带 `-H`，比对解析文件数 | 「编得过」不等于「省了东西」——实测有大量候选承诺省 27 万行，实际差 0 |

只用第一条，会把空头承诺算成成功（这是本轮最重要的发现之一）。

## 1. 与竞品的精度差距（具体，不含糊）

| 维度 | 竞品做到什么程度 | 我们原来的水平 | 本轮之后 |
|---|---|---|---|
| 候选定位粒度 | IWYU / clang-include-cleaner 给到「符号级」：哪个 use 需要哪个 include | 只有 `(TU, 头文件)`，**行号全部为空**（`-H` 不报行号，我们没兜底）→ 报告写「行号未知」 | 行号落到具体行；同名头有歧义时明确拒绝（不猜） |
| 声称的收益 | Header Hero 只给排序，不承诺「删了省多少」 | 承诺「省 N 行」，但 N 来自**会误算的闭包**：60 条里 23 条（38%）实际一个文件都没少 | 只剩 1/38（2.6%）|
| 可删判定 | IWYU 用 AST 判必需性，准确但只支持 Clang 系 | 文本启发式，且只问「源码有没有提到闭包里的符号」→ doctest 上 **60/60 全判「在用」**，零区分度 | 只认「消失集合是唯一供给者」的命中；`plausibly_unused` 2/2 正确 |
| 排序把什么放前面 | Header Hero 按行数排 | 同样按估算收益排 → 第一条真能删的在第 **35** 位 | 第 **1** 位 |

一句话：竞品赢在「语义级判定」，我们原来两头都不占——判定是文本的，闭包还是错的。

## 2. 改了什么

### 2.1 供给者唯一性（判定）

命中一个标识符只能说明「TU 用到这个名字」，不能说明「它来自这条 include」。
旧规则看到「闭包声明 + 源码提到」就判在用；闭包有 275 个头时，一个 `string`
就足以让整条候选变成「在用」。

新规则：只有当**消失集合是这个符号的唯一供给者**时，命中才算依赖证据；
否则记为 `cross_provided`，不构成保留理由。

### 2.2 潜在供给边（闭包）

`-H` 只记录每个头**首次生效**的包含点。`type.h` 里那句
`#include "prelude.h"` 在 `type.cpp` 先包含过之后被 guard 吞掉，树里没有这条边，
于是「删掉 `type.cpp` 的直连会带走 275 个头」——实际一个都没少。

修法与边级归因同源：成本仍用有效树（一个头只解析一次才叫成本），**删除预测**
另建一张按路径的潜在供给图（文本补边，同名且无法相对定位时不猜）。

### 2.3 重命名宏：两侧语义不同（本节经历了一次自我纠正）

第一版把「重命名宏」从**所有**供给集合里剥掉（`#define inflate_fast
z_inflate_fast`，zlib 的 `zconf.h`）——修好了 inffast.c 那条，却制造了新的
误报：zlib `test/minigzip.c` 删掉 `fcntl.h` 后 `O_BINARY` 未声明，而
`fcntl.h` 里的 `#define O_BINARY _O_BINARY` 恰好长得像重命名宏，唯一的
证据被误杀，判成可删。

正确规则是**按检查方向区分**，同一个语法形式在两侧语义相反：

* **被删闭包一侧**（`analyse_usage` 的命中表）：`#define X Y` 是在**定义**
  宏 X，宏随头一起消失 → X 就是它提供 → 用完整 `header_ids`；
* **幸存头一侧**（graph.py 的 `reachable_counts`）：别名不能证明展开目标
  Y 在删除后仍然有声明 → 用剥掉别名的 `header_provider_ids`。

两个方向都各有一个真实工程案例背书：fcntl.h/O_BINARY（闭包侧必须不剥）、
zconf.h/inflate_fast（幸存侧必须剥），各自有回归测试。

### 2.4 行号：扫描期就定位

`-H` 与 `/showIncludes` 都不给行号。把 verify 里已有的「强匹配（路径后缀）→
弱匹配（文件名）→ 有歧义就放弃」抽成 `heavyheader.includes`，扫描期直接填入
`RemovalCandidate.line`。报告从「行号未知」变成可点击的那一行，下游
verify / blame 也不必各自重算。

### 2.5 同一行只算一个候选

zlib 把同一份源码编两次（静态库 + 动态库），旧实现在 87 条候选里重复列出 4 条。
代价要按编译次数算，但**待改的代码行只有一条**。

### 2.6 行号歧义时列出全部位置

`minigzip.c` 的 `<stdlib.h>` 在两个条件编译分支里各有一处（34、47 行），
唯一行号定不出来。旧口径只给「行号未知」；现在把全部候选位置列进 note——
静态判定不了哪个分支激活，但读者不该只看到「未知」。

## 3. 对照（同一台机器、同一份编译数据库、同一份基准脚本）

基准脚本 `experiments/candidate_precision.py`；「改动前」用 `git worktree` 取
`1e1fb43`，并给基线补上同一套行号定位（否则它测不出解析量，对照不公平）。

### doctest（24 TU，clang 23.1.3）

| 指标 | 改动前 | 改动后 |
|---|---:|---:|
| 候选数 | 60 | **38** |
| 有用（编得过且真省文件） | 6 | **6**（一条没丢） |
| 空头承诺（编得过但省 0 个文件） | **23** | **1** |
| 编不过 | 31 | 31 |
| `plausibly_unused` 的正确率 | —（一条都没有） | **2/2** |
| 首条真有用的位置 | 35 | **1** |
| P@5（当前排序 / 纯行数） | 0% / 0% | **40% / 0%** |

### zlib（35 TU，clang 23.1.3）

| 指标 | 改动前 | 改动后 |
|---|---:|---:|
| 候选数 | 87（含 4 条重复） | **47** |
| 有用 | 2 | 2 |
| 空头承诺 | 0 | 0 |
| `plausibly_unused` 假阳性 | 4 | **0**（重命名宏两侧规则修正后，fcntl.h 那条也回到 in_use） |
| 首条真有用的位置 | 52 | **27** |

zlib 的静态判定与真值现在完全一致：45 条 in_use 全部真实编不过（zlib 内部头
本来就必需），2 条真有用的属于保守误判（判 in_use 实际可删），方向安全。

## 4. 未解决 / 已知边界（照实写）

1. **zlib 的 P@5 仍是 0%**：47 条候选里 45 条编不过——成熟 C 库里能删的 include
   本来就极少。本轮的贡献是「不再谎报收益、把真能删的从第 52 位提到第 27 位」，
   不是「把它变成高命中率」。
2. **~~1 条 truth 不一致~~（已查清，是基准脚本自己的坑）**：早先手工复现
   `fcntl.h` 删除得到 rc=0，与探针的 compile-error 矛盾。真相是手工复现的
   命令替换没生效——`entry["file"]` 是正斜杠、命令串里是反斜杠，`str.replace`
   没命中，实际编译的是**原文件**。探针是对的（`O_BINARY` 未声明）；这条
   教训写进了复现注意事项：替换编译命令里的源路径必须先归一化分隔符。
3. **doctest 剩 1 条空头承诺**（`context.cpp:3 -> reporter.h`），潜在图近似导致，
   未修。
4. **文本层的固有上限**：命名空间、重载、`#if 0`、条件编译里的使用看不到。
   `plausibly_unused` 只说「疑似」，最终仍必须由 `verify` 真编译定论。
5. **只覆盖「删」不覆盖「加」**：IWYU 会建议补 include，我们没有。这一侧仍是空白。

## 5. 复现

```bash
python experiments/candidate_precision.py \
  --project <工程> --db <compile_commands.json> --compiler clang++ \
  --out experiments/results/candidate-precision-<名字>.json
```

脚本会打印同上的表格；JSON 里逐条记录了 `usage` 判定、`parse_shrink`、
真实结局与排序位置，便于二次分析。
