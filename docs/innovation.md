# 独创性说明：反事实构建实验（Counterfactual Build Experiment）

> 本文回答评审第一项（技术创新，30%）的三个问题：**技术路线独创在哪、解决了什么
> 既有方案未覆盖的问题、相较同类的明确优势是什么。** 每一条主张都附仓库内可复现的
> 证据；没有证据的主张写进「不声称清单」，不放进正文。
> 日期：2026-10-19。证据等级沿用 [`competitor-matrix.md`](competitor-matrix.md)
> 的定义（D 官方文档 / C 源码核验 / L 本地实测 / ? 未验证）。

## 0. 一句话

> **HeavyHeader 把「删掉这行 include 会怎样」从经验猜测变成一次可复现的受控实验：
> 候选由真实编译器的依赖树按边际收益选出，收益由交替 A/B 实测越过噪声线才成立，
> 结论是三态、带证据、可审计的。**

这个范式有一个名字：**反事实构建实验（CBE）**。竞品回答的是「谁贵」「缺什么」
「还能不能编」；我们回答的是一个**反事实问题**——「如果这行不存在，构建到底会快多少，
这个差异是不是噪声」。这个位置在本轮的竞品尽调里是空的（§2）。

## 1. 既有方案各自停在哪一句

| 范式 | 代表 | 答到哪一句为止 | 答不了的下一句 |
|---|---|---|---|
| 代理指标排序 | Header Hero（2011）、IncludeGuardian | 「谁可能贵」（行×次数、token 口径） | 删了到底快多少；排序本身与实测成本只中度相关（ρ 0.68 / 0.57，[`benchmark-report.md`](benchmark-report.md) §8） |
| 描述性 trace | ClangBuildAnalyzer、MSVC C++ Build Insights | 「现状是什么」（逐头文件累计 ms） | 「删了会怎样」——它只描述已经发生的构建 |
| 二值验证 | deheader（2010） | 「删了还能编吗」 | 「值不值得删」——不测时间，没有收益阈值 |
| 语义正确性 | IWYU、clang-include-cleaner | 「该不该包含」（AST 级） | 成本量化——同工程实测它给 0 条删除建议、101 条补充建议（[`experiments/results/competitor-20261018.md`](../experiments/results/competitor-20261018.md)） |
| **反事实实验** | **HeavyHeader** | 「删了的净收益是多少，有多大把握」 | ——（精度边界见 §5，我们主动写出来） |

**空白是真实的，且是同一道题的下一个自然步骤**：一个维护者拿着 CBA 的排序，
下一步必然是「那我删一个试试」——试完他必须自己回答「快了 3% 是真快还是这回机器闲」。
deheader 停在「还能编」，没有任何工具帮他回答后半句。我们把这一步做成了协议。

## 2. 什么是「反事实构建实验」

一次 CBE 有五个部件，缺任何一件结论都会错（每件的错误形态都有实测记录，§4）：

1. **反事实构造**：把一行 include 注释掉，其余一切不变——编译器真实重编，
   不是模拟。原始文件一个字节不动（`verify` 只写临时目录）。
2. **边际归因选候选**：删一条 include 的净收益不是「这个头文件多少行 × 被包含几次」，
   而是**删掉它之后只有它拉进来的那批头**（独占闭包）才停止被解析。还能从别的路径
   到达的头，删这行不省钱。这是图上的「边删除边际收益」，不是「节点成本」——§3.1。
3. **统计判定**：交替测量（B/P/B/P 进同一时间窗）、每侧 min-of-3、会话内校准的
   噪声线、improved 强制复测——§3.2。
4. **三态结论**：建议删除 / 保留 / 需人工判断，每个结论按功能影响、维护成本、
   构建体验三个维度列证据；未实测的候选显示「未实测」，不猜——§3.3。
5. **可审计**：报告附完整复现命令；负面结果与竞品对照全部公开——§5。

## 3. 三项可核查的创新点

### 3.1 边际归因：从「节点成本」到「边的删除净收益」

归因行数（`行数 × 包含次数`）衡量的是**节点**成本，公式来自 Header Hero（2011），
这一点在 [README](../README.md) 与 [`competitors.md`](competitors.md) 里都写明出处。
我们在这之上加的是**边**的视角：

- **独占闭包**（`attrib/graph.py`）：删掉 include 边 e 后不再被解析的文件集合，
  才是这次删除的净收益。一个头还能从别的 include 到达，删当前这条**不省钱**。
- 它的直接产品化是**白卷诊断**（`attrib/diagnosis.py`）：0 条候选时不交一张空表，
  而是逐条给出被拦原因与标识符证据。实测：nlohmann/json 369 条、zlib 58 条
  收益非零的 include 行被逐条判过——68 条真依赖（带标识符）、299 条位于系统/第三方
  头内部、2 条无法判定（[`g2-diagnosis-*`](../experiments/results/)）。

**先例必须交代（2026-10-19 专项搜查后的校准）**：按 include 边计算删除收益，
**Include-Wrangler（2012，lukedodd/include-wrangler）已经做过**——它的
`include_costs` 输出就是「每条 include 指令省略后能少打开几个文件」，即文件数口径的
边级边际收益；IncludeGuardian 按 token 估算最贵单条 include；clang-build-profiler 与
MSVC Build Insights 的 Include Tree 呈现过逐边解析耗时（树形累计口径）。逐格出处见
[`competitors.md`](competitors.md) §0 校准表。

因此本项目的差异化声明收敛为两句话：**① 口径升级**——上述先例全部停在文件数 /
token / 树形累计耗时；我们把「独占闭包 × trace 自耗时」相乘，得到每条边的
**净收益毫秒预测**（2026-10-19 全网搜查未见先例，待 v0.4 spike 验证）；
**② 数据来源**——我们的依赖树取自真实编译器 `-H`，不是自写扫描器（Include-Wrangler
的正则方案会漏宏与条件编译，Header Hero 的作者自己写明了这个副作用）。
证据等级：L（本机实测，三个工程）。

### 3.2 测量科学：编译耗时的 A/B 实验协议

「注释掉、重编、计时」这个动作 deheader 2010 年就做了。我们的增量是把它从
**一次性测量**变成**带统计判据的受控实验**，并公开协议与全部负面结果：

| 协议部件 | 解决什么 | 实测依据 |
|---|---|---|
| 会话内校准噪声线 | 「跑一次 A/A 就定阈值」是错的：噪声底随机器负载漂移，同一脚本两次跑，单 TU 极差中位 1.58% → 3.68%（[`aa-20261018`](../experiments/results/aa-20261018.md)） | L |
| 每侧 min-of-3 | 噪声只会让测量变慢，不会变快；min-of-3 后单 TU 极差中位 0.72%、p90 1.89%、最大 2.63% | L |
| **交替测量** B/P/B/P | 先测完基线再测补丁，会把测量期间的机器漂移整块算成收益：聚合 A/A 差 **2.005%** → 交替后 **0.644% / 0.245%** | L |
| 双噪声线 | TU 级 2% / 聚合 1%——分母不同，混用会放松或收紧标准 | L |
| **improved 强制复测**（默认 2 遍） | 同一批候选连测三次，读数在 1.04%–2.10% 间摆动，improved 出现 1/3 次；第一轮 improved 的候选复测 **0/4 复现** | L |
| 单遍读数不作数 | 一条单遍 3.738% 的候选，复测后 −0.548%，判 no-change——只看单遍会推荐一个假优化 | L |

这套协议的价值用一个数字说明：**没有它，白卷诊断里 3.7% 的「收益」会被当成结论推荐出去。**
在 C/C++ 构建工具的生态里，我们没有找到把 A/B 实验设计（校准、交替、复测、
阴性结果公开）作为产品协议实现并公开全部负面结果的工具（?——本轮尽调范围：
Header Hero、CBA、Build Insights、IWYU、IncludeGuardian、deheader、CompileScore、
clang-build-profiler、include-what-costs、Include-Wrangler、ReSharper 包含分析器，
2026-10-19 补充搜查后仍未见）。

### 3.3 三态结论与审计形态

候选池的精度是已知短板（222 个候选里 187 个编译不过——这个数字我们主动报，
见 §5）。三态决策层是这个现实的产品化回应：**「能给明确结论」不等于「结论都对」，
但「每条结论都带三维度证据、可复现、可证伪」本身就是竞品没有的形态。**

实测（[`decision-20261018`](../experiments/results/decision-20261018.md)，222 个
候选全部真实编译）：**建议删除 1、保留 187、需人工判断 34**，没有一条停留在「疑似」。
唯一「建议删除」的三个维度全部实测：编译时间 −43.5%、编译器内存 −43.9%、
目标文件体积 −0.05%（阴性结果也如实列出）。

三个配套形态同样只此一家（L）：

- **白卷不是沉默**（§3.1）：0 条候选时给原因清单，不是空表；
- **门禁指名道姓**：`gate` 失败时报出是哪三个头文件、哪些 include 行引入的
  （`include/bloated.h 0 -> 22312 lines (+100.0%)`），不是一个「成本回归 +12%」；
- **门禁挡住「越坏越绿」**：实测过注入导致 TU 从 2 掉到 1 时总成本算出 −67.7%、
  门禁通过——构建坏得越彻底越容易过。已修：可用单元少于基线直接失败
  （[`benchmark-report.md`](benchmark-report.md) §10.3）。

### 3.4 commit 级成本归因（成本考古）：第一个单件首创

上面三项都是「组合层面」的创新——每块拼图都有先例。2026-10-19 的专项搜查
（GitHub repo search + 官网 + 学术，见 [`competitor-matrix.md`](competitor-matrix.md)
§2.3）找到一个**单件层面空白的 capability 并已实现**：把头文件成本回归归因到
具体 commit、文件与 include 行（`blame` 子命令）。相邻工具全部停在不同的问题上
（Jenkins build-time-blame-plugin 分析控制台历史、build-blame 剖析单次构建、
Bencher / cpp-compile-overhead 只做耗时趋势），没有一家做「成本变化 → 谁改的」。

做法：`scan` 在 git 仓库里运行时自动记录 commit；`blame` 对两份基线算逐头文件
成本差，用 `git diff` 解析 include 行变化，再用**「可达该目标且新增/失去它的 TU
集合完全一致」**的模式匹配确定影响半径，预测值 = `Σ行数 × |TU 集|`。预测与实测
在报告里分行列出、不相加；解释不了的部分进「未解释」，不硬分派。

端到端验证（真实 git 仓库 + 真实扫描基线，非构造数据）：一次跨 TU 的新增包含边
导致总量 +56,487 行（+27.4%），`blame` 精确指名 commit、文件与 include 行，
**预测 +56,485 = 实测 +56,485（high）**；剩余 +2 行是被改文件自身的行数增长，
如实留在未解释里。复现与构造记录见
[`experiments/blame_probe.md`](../experiments/blame_probe.md)。

## 4. 为什么这不是「堆叠现成工具」
评判「组合」与「创新」的标准有一条可操作：**拿掉组合中的任一层，结论会不会错。**
本项目对每一层都做过或记录过消融视角的证伪条件：

| 拿掉什么 | 得到的错误结论 | 出处 |
|---|---|---|
| 独占闭包判定 | 按「全项目可省行数」排序把「所有单元都必需的头」排第一；实测按收益排序的前 5 个候选**全部编译失败** | §v0.3，[`experiments/README.md`](../experiments/README.md) 第三节 |
| 交替测量 | 2.005% 的机器漂移被报成优化收益 | [`g2-interleaved-aa-doctest-20261018`](../experiments/results/) |
| 强制复测 | 第一轮 4 条 improved 复测 0/4 复现；3.738% 单遍收益是噪声 | CHANGELOG `--confirm` |
| 三态/决策层 | 用户拿到 187 条「疑似未使用」的假阳性，工具失去可信度 | [`decision-20261018`](../experiments/results/decision-20261018.md) |
| 白卷诊断 | 0 候选被误读成「构建没问题」，而真相是「每条都被判过、都删不动」 | [`g2-diagnosis-*`](../experiments/results/) |
| 门禁的最小 TU 保护 | 构建损坏时成本「下降 67.7%」→ 门禁放行 | §10.3 |

组合不是把工具串起来，是**把每一步的失败模式都消融过、并把证伪条件写进协议**。
这也正是「简单堆叠现成工具得分较低」的反面：堆叠不统计噪声、不复测、不公开负面结果。

## 5. 诚实边界（与正文同样重要）

逐条出处与不声称清单，完整版在 [`competitor-matrix.md`](competitor-matrix.md) §5：

- **归因行数与 Blowup Factor 的公式**：Header Hero（Bitsquid，2011）；
- **「注释掉再编译」**：deheader（ESR，2010）；
- **逐头文件累计耗时**：ClangBuildAnalyzer（`-ftime-trace`）；
- **逐 include 成本着色/聚合**：CompileScore（VS 扩展）；
- **按边计算删除收益（文件数口径）**：Include-Wrangler（2012）——本项目此前
  「未见先例」的表述已据此撤回，改为「毫秒口径的边级净收益预测未见先例」；
- **AST 级必需性判定**：IWYU / clang-include-cleaner；
- 不声称「首个/唯一做头文件成本分析」「建议最全」（IncludeGuardian 更全）、
  「计时最准」（`-ftime-trace` 更细）、「自动优化」（三工程 1/16、1/16、0/16）、
  「比 CBA 更准」（7/10 重合、ρ 0.68，同构口径实测）；
- 已知精度短板：候选池 222 条里 187 条编译不过（文本启发式 vs AST 的差距，
  竞品交叉实验如实记录：clang-include-cleaner 恰好在唯一有效那个单元上分析失败，
  它的「0 条删除建议」部分源于没看到这个单元——两边的问题都写进了报告）。

## 6. 评委快速验证路径

```bash
pip install -e .            # 零第三方运行时依赖，Python 3.10+
# ① 反事实实验本体：三态结论 + 三维度证据（约 6 分钟，222 个候选全部真实编译）
python experiments/decision_check.py
# ② 协议部件：噪声底、交替测量、复测（A/A 是内建的空对照）
python experiments/aa_noise.py --runs 3 --tus 25
# ③ 完整构建收益：63 个 TU，两臂各 5 次干净构建，断言逐个一致
python experiments/run_experiment.py
```

原始数据（每轮秒数、逐单元读数和判定）都在 `experiments/results/*.json`，
渲染出的 Markdown 可由 JSON 重生成，不重跑构建。
