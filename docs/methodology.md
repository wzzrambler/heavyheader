# 方法论：这些数字是怎么算出来的

这份文档定义 HeavyHeader 报告的每一个指标。**如果一个指标没法在这里查到定义，那它不应该
出现在报告里。**

## 0. 总原则：不自己解析 C++

工具不写预处理器、不写词法分析器。它让真实编译器报告自己做了什么：

| 问题 | 怎么问 |
|---|---|
| 你包含了什么，嵌套多深？ | GCC/Clang `-H`，MSVC `/showIncludes` |
| 时间花在哪？ | GCC/Clang `-ftime-report`，MSVC 墙钟计时 |
| 哪些头文件缺 include guard？ | `-H` 输出的 trailer |
| 完整的依赖清单？ | `-M` / `-MM` |

一次编译同时拿到前三项——`-H` 和 `-ftime-report` 都写 stderr，可以并行收集。
这很重要：第二次编译会让扫描耗时翻倍，更糟的是两次编译之间头文件若发生变化，
两边数据会互相矛盾。

## 1. 归因行数（Attributed Lines）

```
attributed_lines(h) = line_count(h) × tu_reach(h)
```

`tu_reach(h)` 是至少间接包含过 `h` 的编译单元数量。

**为什么这个指标有意义**：C++ 项目的预处理与解析成本，一阶近似正比于「编译器被迫读了多少
头文件文本」。每个被解析的头文件，在每个引用它的编译单元里贡献一次自己的行数。所以这个
乘积就是「整个项目为 `h` 付出了多少行解析量」。

**它的局限**：行数不等于解析难度。一个 100 行的重型模板头可能比 1000 行的纯声明头更慢。
它是一个**相对排序**用的指标，不是绝对耗时的预测器。

### 1.1 来源：这个公式不是我们发明的

`attributed_lines = line_count × inclusion_count` 与 **Blowup Factor**
（`Total Parsed / Total Lines`）都来自 Niklas Frykholm 的 **Header Hero**（Bitsquid，2011）：

> "Below the summary are a list of the header files sorted by how many lines they
> contributed to the Total Parsed number. In other words, the size of that file
> multiplied by the number of times it was included."
> —— <http://bitsquid.blogspot.com/2011/10/caring-by-sharing-header-hero.html>

本工具的 `total_included_lines()` 即其 `Total Parsed`；`blowup_factor()` 即其
`Blowup Factor`。两者在 Markdown 报告与 JSON 中都显式导出分子与分母，读者可自行验算，
不必相信我们给的比值。

**唯一的实质差异在「包含次数从哪来」**：

| | Header Hero | HeavyHeader |
|---|---|---|
| 依赖来源 | 正则匹配 `#include` 行；作者自述不运行真实预处理器 | 真实编译器的 `-H` / `/showIncludes` 依赖树 |
| 宏、条件编译、`#include_next` | 会漏（作者已在原文注明） | 以编译器实际打开的文件与次数为准 |
| 算完成本之后 | 排序到「谁贵」为止 | 继续做反事实重编，量化删掉之后的收益 |

正则方案的代价是准确性，收益是速度（秒级扫完大工程）；我们的取舍正好相反。
完整对标、逐条出处与核实日期见 [`competitors.md`](competitors.md)。

## 2. 独占闭包（Exclusive Closure）

删掉 TU `t` 中的一条直接 include `d` 后，唯一会停止被解析的头文件集合：

```
shared(d)    = ⋃_{d' ∈ direct_includes(t), d' ≠ d} closure(d')
exclusive(d) = ( closure(d) \ shared(d) ) ∪ ( {d} 当 d ∉ shared(d) )
```

**这是本工具与普通 lint 工具的本质区别。** 一个头文件如果能从别的 include 到达，那么删掉
当前这条 include **并不会**让它停止被解析——钱已经花了。只有独占闭包里的头文件才是删掉
这条 include 的真实收益。

**为什么公式里要显式把 `d` 自己加回来**：`closure()` 回答的是「这个头能到达什么」，
按设计不含起始节点（见 `test_closure_excludes_the_start_node`）。而删掉一条 include
停止解析的不只是它拖进来的东西，**还包括 `d` 自身的文本**。漏掉这一项时，一个不 include
任何东西的「叶子头」独占闭包为空、预计收益为 0，于是被 `saved < min_savings` 直接丢弃——
`scan` 会说「删它毫无收益」，而 `verify` 实测同样一个头却能量到真实的提速。两个命令自相
矛盾，且被漏掉的恰好是最常见的一类优化：删掉一个没人用的独立头文件。

只有当 `d` 自己也在 `shared(d)` 里（别的 include 已经付过钱）时才不加回来——那种情况下
删掉这条 include 确实一分不省。

> **实现注记（一个真实的 bug）**：早先版本把 `d` 自己也放进了「已付费」并集，
> 导致每个候选的独占集合恒为空，于是所有项目都报告「没有可优化项」。
> 这个症状与「确实没问题」在输出上完全无法区分，因此靠单元测试而非代码审查来防守。
> 见 `tests/test_attribution.py::test_exclusive_closure_is_not_emptied_by_the_candidate_itself`。

## 3. 重复解析检测（缺 include guard）

```
redundant(h) = inclusion_events(h) > tu_reach(h)
```

`inclusion_events(h)` 是编译器**实际处理** `h` 的次数。

**为什么这是确定性信号**：`-H` 只为**实际处理过**的包含打印一行。带 `#pragma once` 或
guard 宏的头文件，第二次及以后的包含会被跳过，因此无论多少个头文件包含它，`-H` 里只出现
一次。于是「同一编译单元内出现多次」在物理上只可能是缺少 guard。

修复（补 guard）**永远安全**，且收益立竿见影——这是报告里唯一标为「必赚项」的分类。

## 4. 预计节省（Estimated Savings）

```
estimated_lines_saved = Σ_{h ∈ exclusive(d)} line_count(h)
estimated_percent = estimated_lines_saved / processed_lines(t) × 100%
```

`exclusive(d)` 含 `d` 自身（见上一节），`processed_lines(t)` 是该编译单元实际解析的全部
头文件行数之和。

**只有项目自己的头会进入候选清单。** 系统头与第三方头照常出现在统计表里（这样各项数字才
加得起来），但从不作为「可删除」建议——`<vector>` 不是我们能改的东西，一条以「建议删除
`<vector>`」开头的排序清单会把所有可执行项都埋掉。这条契约在 `HeaderKind` 与
`classify_headers` 的文档字符串里各写了一遍。

## 5. 实测节省（Measured Savings）

来自 `heavyheader verify`，是唯一**不经过模型**的数字：

1. 把候选 include 行**注释掉**（不是删除——实验必须可逆，diff 必须可审查）；
2. 在临时目录重新编译，flags 与原扫描完全一致，并额外把原文件所在目录加进
   `-I`（因为 `#include "..."` 是相对于**包含它的文件所在目录**解析的，
   从临时目录编译会丢失兄弟头文件）；
3. 每侧重复 N 次，取**最小值**。

**为什么取最小值**：噪声只会让测量变慢，不会变快。因此最小值是最接近真实成本的估计。
取平均值会让负载波动直接进入结论。

**什么算「有效」**：相对差异 ≥ 2%。单文件编译时间的噪声地板就在这个量级，
把 1% 的波动报告成优化成果是不诚实的。

**注释哪一行（同名头的处理）**：一个项目里出现两个同名头文件（`util/thing.h`
与 `other/thing.h`）并不罕见，而只按文件名匹配会把它们当成同一个。定位规则
按可信度排序：

1. **编译器上报的行号**（`RemovalCandidate.line`）——最权威。但 GCC/Clang 的
   `-H` 输出只有 `. header.h`、不含行号，MSVC 的 `/showIncludes` 同样不报，
   所以这条路径目前只在工具链支持时生效；
2. **完整路径后缀匹配**——`#include "other/thing.h"` 的文本本身就是路径，与
   候选头的完整路径做后缀比较即可区分同名头。这不是重新实现预处理器：不做
   宏展开、不算条件编译，只是路径后缀比较；
3. **文件名匹配**——仅当上面两条都定不下来时使用。

**定不下来时宁可不验证。** 若仍有 ≥2 行候选，状态报 `ambiguous` 并跳过；
绝不「取第一行的近似」。删错一行的代价不是实验失败——而是 verify 给出一条
看起来可信、实则指向另一个文件的结论，那比不验证更糟。同名头同时出现在
结果里时，输出会补上一级目录以区分。

## 6. 使用状态启发式（Usage Heuristic）

对 TU 源码和头文件分别提取标识符（剥离注释、字符串、字符字面量），交集非空则记为一次
「命中」。两侧都用**宽口径**：正文里出现过的每个标识符都算，连参数名、成员名也算。

宽口径不是偷懒。命中只说明「源码出现了这个名字」，它能不能当作依赖证据由后面两步决定：
**供给者集合语义**（§6.3 的 `declarers`——这个名字在幸存侧还有没有声明者、是不是别名、
是不是只活在本次编译看不到的条件区）和**编译器内建词表**（`_MSC_VER`、`__attribute__`
这类不可能随任何头文件消失的名字，直接剔除）。宁可多记一次命中、在判定阶段否掉它，
也不要在提取阶段漏掉它——漏掉之后这条真依赖就没有任何证据了。

`attrib/decls.py` 里另有一个**按声明作用域**提取的实现（`declared_names`：括号深度 0、
无类体/函数体包裹、预处理行跳过、`#define` 的宏名单独收集；libstdc++ 的
`basic_string.h` 名字数从 1173 降到 81，成员名消失、类名保留），并有单元测试覆盖。
它针对的是同一类问题的另一端——参数名 `size` 被当成 `<stdlib.h>` 的声明、成员名 `at`
被当成 `<string>` 的声明——但换上去改的是**命中集合本身**，而 2026-10-19/20 那三轮精度
工作（三语料零假阳性、G2 闭环命中率）是用宽口径 + 集合语义这一版跑出来的数字，换口径
就得全部重跑才成立。所以它是**已实现、未接入判定**的能力：当前判定走宽口径 + 集合
语义，同类误判由内建词表与 `declarers` 消解。这个选择记在 CHANGELOG 里，没有藏起来。

**已知误报来源**，按常见程度：

| 模式 | 为什么会误判 |
|---|---|
| 为副作用而包含（`<iostream>` 的流初始化） | 头文件不声明源码会用到的名字 |
| 纯 include 聚合头 | 它的「标识符」是它转发的名字，直接包含者可能一个都不用 |
| 纯宏头（`#define` only） | 宏可能被别的头文件使用 |
| 类型经模板参数、ADL、`using` 间接到达 | 文本上看不出关联 |

因此：**报告永远标注这是启发式，`verify` 才是权威。** 工具不自动删任何东西。

### 6.4a 下游引用证据（头文件级候选）

头文件级的删除改变的是**所有**包含者的可见性，只问 owner「用不用」不够。
每条头文件级候选因此带一份**下游引用**证据：除拥有这一行的文件之外，
还有哪些文件的名字来自即将消失的集合。

它**不是判定，也不是预测**——doctest 17 条候选的实测是失败组 8/8 有引用、
通过组 8/9 也有引用（Fisher p≈1.0，`experiments/results/g2-probe-decls-doctest-20261018.md`）。
它的作用是解释：删这一行会牵连谁、verify 要重编谁、失败时该去哪个文件看。有下游引用的
候选置信度一律压到 low；判定仍然只由 `verify` 给。

> 那份归档跑在**声明级口径的实验分支**上（候选池 17 条），与主线 G2 的 16 条
> 不是同一口径，两组数字不能混用——引用它只是为了说明「下游引用没有预测力」
> 这个**否定性结论**，不是拿它当采纳率证据。

## 6.5 删除建议决策层（Removal Advice）

启发式回答「这个头还用不用」，是个可能性问题；开发者问的是「这行值不值得删」，
是个决策问题。`attrib/advice.py` 把探针证据收敛成三个明确结论之一，
规则是确定性纯函数（`tests/test_advice.py` 逐路径覆盖）：

| 证据 | 结论 |
|---|---|
| 没有探针结果 | 需人工判断，无倾向（没测过就不下判断） |
| 实测编译失败 / 定位不到该注释哪一行 | 保留 |
| 编译通过但未计时（`--probe` 只问能不能编） | 需人工判断，无倾向 |
| 编译通过且耗时下降 ≥ 噪声线 | **建议删除** |
| 编译通过但收益在噪声内 | 需人工判断，附倾向 |

「需人工判断」不是模糊态：它说清楚缺哪个证据，并且当剩余证据指向一边时给出倾向
（偏删/偏留）。倾向阈值 `MAINTENANCE_LEAN_LINES`（默认 1,000 行）是**策略值**
——「多少行不再被解析值得一次 review」，不是物理常数，团队可以不同意并改掉它。

每个结论按三个维度列依据：**功能影响**（编译通过/失败、消失的标识符由谁提供）、
**维护成本**（独占闭包规模、全项目还有几个使用者）、**构建体验**（实测秒差、
GGC 内存差、目标文件体积差）。三个维度的数字全部来自实测；工具链不提供的维度
写「该工具链不提供」，**不写成 0**。

**编译通过 ≠ 功能正确。** 「建议删除」的全部含义是「这个编译单元不带这行也能编、
而且更快」；跑测试是开发者的步骤，报告里明写这一条。

**噪声阈值只有一份。** `TIME_NOISE_FLOOR`（2%）定义在 `attrib/advice.py`，
`verify` 反向 import——状态列的 `improved` 与结论列的「建议删除」共用同一个
「什么叫提升」的定义。两份副本就会漂移，然后报告里出现「实测 improved 但不建议删」
这种自相矛盾。

## 6.6 计时口径：编译器 TOTAL、墙钟、与「0.0 陷阱」

`-ftime-report` 的 TOTAL 行是编译器内部计时，精确但会坏：GCC on MinGW 对某些
头文件（`<windows.h>` 等）会打印 `2**64/1e9` 秒这种物理上不可能的值，
`sanitise_timings` 会把超墙钟的行丢掉。**如果 TOTAL 因此缺失而不做处理，
`total_wall_seconds()` 返回 0.0——一个「移除后 0 ms」会被任何下游读成 100% 收益，
那是把坏掉的计时器当成完美优化。** 驱动层因此做了回退：TOTAL 不可用时，
补一条我们亲自量的墙钟 TOTAL 行，并在 `timing_discarded` 里写明「编译器自报计时
损坏，改用墙钟」。两种口径不同，`VerificationResult.timing_note` 把这个区别
一直带到报告的「实测有效的改动」表下面。

## 6.7 一个曾污染所有计量的 bug：源文件被传了两次

`compile_commands.json` 的命令形如 `g++ … -c foo.cpp -o foo.o`。构造任务时只剥掉了
`-o foo.o`，`-c foo.cpp` 留在 flags 里，而驱动又会追加一次源文件——于是 GCC 收到
**同一个文件两次**。GCC 不报错：它安静地把文件编译两遍，打出**两条 TOTAL 行**，
而读取方只取第一条。扫描、探针、基线三层的全部计时与 include 树都建立在这条错误
命令上（include 树则是两棵相同的树被拼成一棵，事件数翻倍）。

2026-10-18 在决策层实验里被抓到：三个候选报出「移除后 0 ms / 节省 100%」——
正是 TOTAL 行丢失后的 0.0 陷阱。修法三处：

1. `scanner._strip_source_token`：构造任务时剥掉数据库自带的源文件 token
   （驱动拥有源文件参数）；
2. `drivers.base._append_source`：第二道防线，extra_flags 里已带该文件时不再追加；
3. `GccLikeDriver.interpret`：TOTAL 缺失时回退墙钟（见 6.6）。

**这个 bug 值得记住的地方**：它不崩、不报错、数字看起来全都合理——只是每个都错。
它能在测试套件下存活，是因为单元测试用的是手写 options，从来不带 `-c <源文件>`。
现在 `tests/test_scanner.py` 与 `tests/test_drivers.py` 各有一条回归测试锁住它。

## 6.8 可选 AST 交叉检查（`--semantic`，ROADMAP v0.3 路线 1）

文本启发式的上限是「猜」：判错一个 token 级用法就会误报。精确判定需要 AST，而把
libclang 做进程内后端（路线 2）在本机被**证伪**——`experiments/libclang_spike.py`
用 ctypes 加载 `libclang.dll` 成功，但每个 TU 创建入口（`clang_parseTranslationUnit`
等）都返回 `CXError_ASTReadError` 且无任何诊断，无法调试。该 spike 已固化为可复现的
负面记录，避免后人重蹈。

剩余可行路线是把 LLVM 的 **`clang-include-cleaner` 作为外部进程**驱动——这正是
`experiments/competitor.py` 已在 63/64 个单元上验证可用的方式。现以 `scan --semantic`
接入正常流水线：

- 对每个**出现候选的单元**跑一次 cleaner（`-p <compile_commands 目录> --print=changes`），
  缓存 per unit，结果写回候选的 `semantic` 字段；
- 设计契约是**只增强、不削弱**：当 cleaner 也把同一 include 列为「可删」时，作为佐证
  写进 REMOVE 理由（`attrib/advice.py::_semantic_reasons`）；cleaner 的**沉默**（没列为
  可删）不等于「在用」——它可能没分析那个 TU，或其启发式与我们不同——因此**绝不**据此
  降级我们的 REMOVE。把沉默当否决，等于把 ctypes 的失败换种方式重演；
- 工具缺失、或它的分析对某个单元失败（`ok=False`），都只写「AST 交叉检查未能提供」，
  结论仍以本工具实测为准。

> 端到端验证（2026-10-18）：对 nlohmann/json 的 `unit-windows_h` 跑 `--semantic`，
> `clang-include-cleaner` 分析该单元**失败**（与竞品对比里「1/64 单元分析失败」一致），
> advice 如实反映「未能提供…结论仍以本工具实证为准」。两个工具在这个单元上互不完美，
> 反而互相印证了「交叉检查必须只增强、不削弱」的设计是对的。

## 6.9 可行性闸门与「白卷」诊断（`--header-sites`）

头文件级候选（`attrib/sites.py`）在进入候选表前要过一道**可行性闸门**：
拥有这条 `#include` 的那个文件，自己正文里不能使用「删掉它就会消失」的标识符。

- 闸门是**文本**判定，与 `usage` 同一套启发式，只是换了分析单元（站点文件自身，
  而不是整个编译单元）；
- 闸门的作用是**排序前的过滤**，不是安全结论：它放行的候选仍然必须由
  `verify` 重新编译全部受影响单元之后才算数；
- 闸门会漏（假阴性）。实测一例：zlib 的 `zconf.h → <limits.h>` 因使用
  `UINT_MAX`/`ULONG_MAX` 被判「在用」，而实测删掉后 15 个单元全通过、仅省
  0.356%。准确的说法是「放行的候选里编译失败 0 条」，不是「不会漏」。
- **闸门对「能不能编」没有预测力**。doctest 上全量探测：放行 16 条通过率
  50%，完全不筛 66 条通过率 47%——统计上不可区分。它真正的作用是把候选
  砍到 1/4、把 verify 成本降到 1/4；在本轮三个工程里，它没有漏掉值得采纳
  的改动（漏掉的 23 条能编候选，初筛唯一过 2% 的复测为 −0.548%）。
  见 `docs/benchmark-report.md` §9.8。

**诊断（`attrib/diagnosis.py`）**：闸门一条都不放行时，扫描仍要能回答「为什么」。
每条收益非零但被拦下的 include 行都记录：

| 字段 | 含义 | 证据等级 |
|---|---|---|
| `amplified_lines` | `独占行数 × 受影响单元数`，与候选表同一口径 | 实测（编译器依赖树 + 行数） |
| `reach` | 解析它的编译单元数 | 实测 |
| `reason` | 拦下原因（真依赖 / 无法判定 / 系统头站点 / 只被一个单元解析 / 已被别处拉入） | 文本启发式 |
| `detail` | 具体标识符与提供者，或「无」 | 文本启发式 |

口径限制，写报告时必须一起说：

- 成本集中度用的是**归因行数占比**，不是墙钟时间占比。一个只占 1.6% 解析行数的
  头文件仍可能占掉可观的模板实例化时间——本诊断不回答这个问题；
- 「项目自有头」按路径是否在 `root` 下判定，vendored 在项目内的第三方
  （如 json 仓库里的 `tests/thirdparty/doctest/doctest.h`）会被算成项目头；
- 诊断**不构成删除建议**，它只是把 0 条候选这个结论解释清楚。

## 7. 墙钟时间（Wall-clock Seconds）

每个编译单元由驱动自行测量 `time.perf_counter()` 差值。

**它是最吵的数字**，随机器、负载、时钟状态波动。因此：

- `gate` **不**用它做判定依据，只做展示；
- 跨机器、跨时段不比较绝对值；
- 趋势图里它和归因行数一起画，但归因行数是主指标。

## 8. 门禁判定

```
regression = (attributed_lines_after - attributed_lines_before)
             / attributed_lines_before × 100%
fail if regression > max_regression_percent   (默认 5%)
```

失败时附带三个最严重的回归头文件及其 `before → after` 行数，让构建日志能直接定位到人。

**默认值刻意保守**：一个在噪声上误触发的门禁会被关掉，而关掉的门禁保护不了任何东西。
5% 是「明显变化」与「正常波动」之间的实用分界。

## 9. 已知局限汇总

1. 行数 ≠ 解析难度（重型模板头的权重被低估）。
2. `-fsyntax-only` 不含代码生成阶段，因此报告里没有「opt and generate」的成本。
   用 `--full-compile` 可以包含它，但扫描会明显变慢。
3. 增量编译（ccache、distcc）会改变耗时分布；在启用 ccache 的环境里跑
   `verify` 需要先清缓存，否则测到的是缓存命中时间。
4. 循环包含在带 guard 的代码里不可能出现，但解析器仍实现了环保护——
   喂给它畸形输入时不会死循环。
5. Windows 路径大小写、符号链接、`subst` 盘符可能导致项目头文件被误判为第三方。
   此时用 `--path` 指定规范化后的根目录。
6. **指标不是原创**：归因行数与 Blowup Factor 来自 Header Hero（2011），
   「注释掉再编译」来自 deheader（2010）。我们只声明组合与实测闭环，不声明单点首创；
   详见 [`competitors.md`](competitors.md)。
7. **建议覆盖度不如 IncludeGuardian**：它有七类结构性建议，我们缺少
   `inline sources`（source 过小、建议并入 header）这一整类，`make private`
   与 `large files` 也没有独立成章。
8. **计时精度不如 `-ftime-trace`**：ClangBuildAnalyzer 能给出编译器内省级的
   逐头文件耗时；我们的实测是墙钟差分加多次取中位数，粒度更粗，换来的是
   跨 GCC/Clang/MSVC 与「删掉之后」的反事实。
9. **`--semantic` 不是 IWYU**：它只是把 `clang-include-cleaner` 的结论拿来交叉
   印证，工具沉默**不等于**该 include 没被使用，因此绝不据此降级结论。

## 10. 增量扫描缓存（`--cache`）

复用上次结论的判据只有一条：**编译器看到的输入没变**。输入包括三项：

1. 编译单元自己的源文件；
2. 它依赖的每一个头文件——取编译器 `-H` 报告的真实传递闭包，不是猜的；
3. 编译选项：编译器、语言标准、宏、flags、包含路径、`--full-compile`。

三者都没变，上次编译的结论（依赖树、包含事件、分阶段计时）就仍然成立。

**文件指纹分两级**：先比 `size` 与 `mtime_ns`，两者都没变就直接判定未改动，
**不读文件内容**（未改动的头文件连打开都不用，这是快路径的关键）；mtime 动过
才计算内容哈希（blake2b）比较——`git checkout`、`touch`、`rsync` 会改 mtime
但不动内容，只靠 mtime 会让整个项目白白重编一遍。缓存里没有内容哈希时
（例如早期格式写的文件），保守地判定为已改动。

**编译失败的单元不进缓存。** 失败通常意味着依赖缺失，而它记录下来的依赖集是
不完整的：等有人把缺失的头文件补上，缓存里那批依赖「看起来没变」，于是会一直
重复报同一个错误。失败的编译还有个特点——编译器遇到错误就中止，本身很快，
重编的代价可以接受。

**两条退化路径**：缓存文件不存在/损坏、或编译选项指纹不匹配时，一律退回全量
扫描。缓存只保留本次扫描涉及的编译单元，不会随项目演进而无限膨胀。

**它的边界**：

1. 条件编译（`#ifdef`）下，宏变了但源码没变的情况由「编译选项指纹」覆盖；
   然而宏若来自某个头文件（如生成的配置头），头文件的改动同样会被依赖指纹
   捕获——这两条合起来覆盖了绝大多数真实场景。
2. 一个全新的头文件只能经由「修改某个已有文件」被引入，而那次修改会被上面的
   判据捕获，所以新文件不需要特殊处理。
3. 包含路径顺序变化（`-I a -I b` → `-I b -I a`）若改变同名头的解析结果，
   指纹会捕获；但如果只是文件系统上多了一个同名头，而包含路径与已有文件
   都没变，理论上存在漏判。这种情况极为罕见，且可用 `--cache` 重跑规避。

## 11. 历史趋势看板（`history` 子命令与 `--serve`）

看板要回答的问题是「我的项目构建成本怎么随时间变的」，而不是「现在这一刻有多贵」。
它的数据来源就是 `scan --history` 每次追加的一行 JSONL，所以不需要任何新存储。

**判定口径与 `gate` 完全一致**：归因行数是主指标（确定性、可复现），墙钟时间只在
图表里做展示（它随机器负载波动，跨机器不可比）。这样「看板上的趋势」和「CI 上的门禁」
说的是同一件事——否则会出现看板显示成本涨了、门禁却说没问题的荒谬情况。

**三个刻意的设计取舍**：

1. **只绑回环地址 `127.0.0.1`**：看板是给一个人、在一台机器上看的，不是拿来网络共享的。
   进程关掉就彻底消失，不留后台 daemon、不装任何东西。多人共享属于另一项「趋势服务」，
   需要持久化存储与多端访问，不在当前范围。
2. **零第三方依赖**：用标准库 `http.server` 起一个只服务单页的临时服务，HTML 自包含
   （内联 SVG 画图，无 CDN、无图表库），和 `report/html.py` 的做法一致——能在最朴素的
   CI 容器里跑，是项目的一条硬约束。
3. **历史文件容错**：它是 append-only 的运行记录，会被手工查看、拷贝、中断写入。一行坏的
   （截断的、夹杂日志的）不该让整个趋势看不了——`load_trend` 跳过坏行/空行/非 dict 条目，
   时间戳缺失或格式不对时回退到序号标签，而不是抛错整页空白。

看板还提供 `--html out.html` 直接导出一份自包含网页，方便挂到内部 wiki 或作为报告附件。

## 12. PR 评论机器人（`pr-comment` 子命令）

把 `compare_scans` 与 `evaluate_gate` 的结论变成一段 GitHub 风格 Markdown 评论，
可选经 `gh` 发布。它是工具「让团队持续用起来」的一环——门禁只让流水线变红，
评论才会把「谁变贵了、为什么」直接送到评审者眼前。

**三个刻意的设计取舍：**

1. **零第三方依赖，发布走 `gh` CLI。** GitHub Actions runner 自带 `gh`，不引入
   `requests`/`PyGithub`，否则就破坏了「能在最朴素的 CI 容器里跑」这条硬约束——
   为一个本就有免费、预装客户端的场景去加一个网络库，不划算。

2. **幂等，不刷屏。** 每条评论都带一个隐藏 HTML marker（`<!-- heavyheader-report -->`）。
   发布前先用 `gh api` 列出该 PR 的评论，找到同一 marker 的旧评论就 `PATCH` 编辑，
   否则才 `POST` 新建。PR 每推送一次就重跑一次 bot，评论被原地更新而不是越堆越长。

3. **优雅降级，绝不静默丢结果。** 没有 `gh`、或环境里取不到 PR 编号（既没 `--pr`、
   也没 `PR_NUMBER`/`GITHUB_REF`），正文照样打印到标准输出，退出码为 2 明确告知
   「发布这步失败」。正文丢失才是真事故，发布失败只是配置问题。

判定口径与 `gate` 完全一致（归因行数为主指标），所以评论里的「未通过 +40.3%」和
CI 里的门禁失败是同一句话。评论正文统一用 POSIX 风格路径（`src/foo.h` 而不是
`src\foo.h`），因为评审在 GitHub 上看，反斜杠只会像一处笔误。

当前只走 GitHub 的 `gh`；GitLab 需要另一套 API 后端，属于同一功能的不同实现。

## 13. 并行编译的瞬时启动失败（偶发 TU 失败的排查）

`scan` 用线程池并行编译所有编译单元，每个单元都是一次独立的编译器子进程。
在负载高、并行度大时，操作系统偶尔会**启动不了**某个子进程——Windows 上常见
`[WinError 1455] 页文件不足` / `[WinError 6] 句柄无效`，POSIX 上是 `EMFILE`
（描述符耗尽）/ `ENOMEM`。这与「这个 TU 本身有错」无关：过一会儿重编就好了。

**为什么这是个隐蔽的 bug。** 这类启动失败以 `OSError` 的形式从 `subprocess.run`
抛出。原本 `driver.run` 只捕获 `TimeoutExpired`（编译太慢）和 `FileNotFoundError`
（编译器不在 PATH），其余 `OSError` 会穿透出去，被 `scan_project` 的兜底
`except Exception` 接住、记成「这个编译单元失败」。于是同一个源码、零改动，
连跑多次时 TU 数会忽高忽低（曾观察到 8→4→8），而看板只在同代码下才可比——
一个本该稳定的数字抖一下，趋势就不可信了。

**修复：只对「启动」做有限次重试。** 关键是把「启动失败」和「编译失败」分开：
编译失败是 `returncode != 0`，走正常的「记成失败」路径，不需要重试；启动失败
是进程根本没起来，重试一两次通常就能成功。具体做法在 `CompilerDriver.run`：

- `FileNotFoundError` → 编译器不在 PATH，必然失败，**不重试**，直接报明确错误；
- `TimeoutExpired` → 编译确实超时，重试只会再等一个超时，**不重试**；
- 其余 `OSError` / `subprocess.SubprocessError` → 视为瞬时启动失败，最多重试
  `_MAX_SPAWN_ATTEMPTS = 3` 次，每次间隔 `_SPAWN_BACKOFF = 0.05s × 尝试序数`；
  次数用尽才当作真正的失败。

重试成功后，把重试次数记到 `TranslationUnit.spawn_retries`，由 `scan_project`
汇总：只要有 TU 是「重试后才成功」的，就在 `scan.warnings` 里提示用户「刚才
差点把这个 TU 误记成失败，若频繁出现可用 `--jobs` 降低并行度（如 `-j 4`）」。
这延续了项目「不静默修正数字、把异常显出来」的一贯原则——重试保住了正确的 TU
计数，但绝不藏着「系统曾经顶不住」这件事。

回归测试：`tests/test_drivers.py` 用替身 `subprocess.run` 模拟「前 N 次抛
`OSError`、第 N+1 次成功」，断言 TU 最终算作成功且 `spawn_retries` 正确；并断言
`FileNotFoundError` 与 `TimeoutExpired` **不会被重试**；`tests/test_scanner.py`
断言「有 TU 重试成功」会触发那条警告。

## 14. 多编译器对比（`toolchains` 子命令）

`scan` 一次只回答「在一个工具链下，成本花在哪些头文件上」。工具链迁移要回答的
是另一个问题：**换一个编译器，是更快还是更慢，差在哪里**。`toolchains` 对同一份
代码依次跑每个编译器，输出一张横向矩阵——每个编译器的 TU 数、归因行数（全部 /
项目头 / 非项目头）、依赖边、耗时与相对最快，以及项目头文件在各编译器间的差异。

**三条口径，避免把矩阵读成它没有的意思：**

1. **耗时只作参考，结构指标才确定性。** 墙钟时间取决于机器、负载、是否
   `-fsyntax-only`，矩阵里的是「本机这次」的实测，用来提示量级，不构成绝对承诺。
   归因行数、依赖边、TU 数由编译器真实报告的 include 图算出，同机多次一致。
   与 `verify` 的 2% 噪声地板同一口径：两个编译器的耗时相对差**小于 2% 时不判定
   谁更快**，只如实说「在噪声范围内」——把 1% 的调度抖动报成「快 1%」比不报更误导。
2. **逐头文件差异只比项目自己的头。** 系统头路径在 GCC / Clang / MSVC 下各不相同
   （`/usr/include/c++/13/vector` vs MSVC 的安装路径），按路径拼接毫无意义；混进来
   只会把「路径不同」误读成「成本不同」。项目头是同一份源码，比它才有意义；系统 /
   第三方头的总量差异体现在「非项目头」那一列。
3. **「成本为 0」必须读成失败，而不是「快得离谱」。** 一个编译器如果一个 TU 都
   没编译成功，它的归因行数与耗时都是 0；若照单全收，它会以「零成本、最快」
   排在矩阵第一。所以判据是「至少一个 TU 真的编译成功」，否则整行标成失败并给出
   原因（没装、全量报错），不参与「谁最快」的比较。

**两个工程取舍：**

- **串行执行。** 并行跑两个扫描会让它们互相争抢 CPU，把墙钟时间抬高——而「谁更快」
  恰恰是这个功能要回答的问题。串行慢一点，但数字可信。
- **缺失编译器优雅降级。** 只装了 GCC 没装 Clang 是常态。矩阵不会整体失败，
  缺失的那个如实写成「失败：找不到编译器」，其余照常对比；不足两个成功编译器时
  明确提示「无法做横向对比」，而不是硬编一个结论。

回归测试：`tests/test_toolchains.py` 用构造的 `header_stats` 覆盖「零成功 TU 记失败」
「只统项目头」「一致的头不进差异表」「无可信耗时不硬评最快」「缺编译器不影响其余」
「渲染与 JSON 结构」。
