# 增量构建税实测（2026-10-18）

- 编译器：`g++`，受控工程 8 个编译单元（顺序编译，无并行）
- 扫描命令：`heavyheader scan --full-compile --jobs 1`

## 一、预测 vs 真实增量重建

| 指标 | 数值 |
|---|---:|
| `core.h` 增量税（预测，扫描期计时求和） | 4.80 s |
| 改动 `core.h` 后真实重编 8 个单元 | 2.97 s |
| 预测/实测 | **1.61×** |
| `mid.h` 增量税（预测，应只含 4 个单元） | 2.41 s |

## 二、扫描开销

| 指标 | 数值 |
|---|---:|
| 不带诊断的完整构建 | 2.80 s |
| 扫描（`--full-compile`，含 `-H` + `-ftime-report`） | 5.59 s |
| 扫描 / 构建 | **2.00×** |
| 默认扫描（`-fsyntax-only`，不做代码生成） | 见 README 基准，显著低于完整构建 |

## 三、结论应该怎么写

- 预测与实测比值 1.61×：主因是 `--full-compile` 会为每个单元额外链接一次，而真实增量构建只编译不链接。这不是公式错，是测量协议缺陷；校准前报告必须标「实验性、未校准」。
- `mid.h` 的税约等于 `core.h` 的一半，符合「只有 4 个单元包含它」的结构——说明税额确实按传递包含关系分配，不是拍脑袋。
- 扫描比完整构建多 2.00× 开销，换来依赖树 + 分阶段计时 + 反事实能力；默认模式只做语法检查，代价更低。

## 口径与局限

1. 税额只含编译、不含链接；真实项目里链接时间不会随头文件变化。
2. 顺序编译用于消除并行调度噪声，不代表 CI 上的实际等待；并行时等待接近「最慢单元」而非求和。
3. 预测值含 `-H` 与 `-ftime-report` 的额外开销，实测值为普通编译——这正是比值不为 1.0 的原因，不应把它当成误差抹掉。
