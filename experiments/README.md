# 竞赛实验：真实工程、完整构建、可复现

这个目录回答评审提的三个问题。**一页纸的答案是：优化效果能量化（完整构建实测
−7.1% 墙上时间 / −11.4% 编译 CPU）；工具的优势在「该往哪使劲」这一层成立，
在「这一行 include 能不能删」这一层，排序已经修好并检验过，但最终判定仍必须
真的编译一次——两个结论都是实测的，都写在下面。**

| 评审问题 | 由谁回答 | 结论（一句话） |
|---|---|---|
| 优化效果能否量化？ | `results/experiment-*.md` | 能。完整构建前后对照，估算（行数）与实测（秒）分两张表，从不合并 |
| 与现有工具相比优势是否成立？ | `results/control-*.md` | 分层成立：方向判断实测支持；单点删除的排序已修，判定权交给 `verify` |
| 评委能否几分钟看懂？ | `docs/demo-walkthrough.md` | 四步：发现热点 → 定位 include → 验证收益 → 阻止回归 |

## 一、实验对象与固定项

不选玩具工程，选一个每天在 CI 里被真实构建的项目：**nlohmann/json v3.11.3**
的测试目标——63 个测试单元 + 1 个共享 `main`，32 万个断言级测试，
源码快照以 SHA-256 固定（`fetch.py` 校验，不符直接拒绝运行）。

| 项 | 值 |
|---|---|
| 工程 | nlohmann/json `v3.11.3`（tarball SHA-256 `0d8ef5af…`） |
| 测试语料 | `nlohmann/json_test_data` `v3.1.0`（按 commit 固定） |
| 编译器 | g++ 16.2.0（MinGW-w64，x86_64-win32-seh） |
| 参数 | `-std=c++11 -O0` + 上游 `tests/CMakeLists.txt` 的三个 define |
| 并行度 | `-j8` 固定 |
| 每臂重复 | 5 次**干净**构建（每次清空目标目录） |
| 正确性门禁 | 63 个测试二进制逐个运行，**逐套件**比对断言通过/失败数 |
| 噪声线 | 变化 < 2% 判为「无变化」 |

为什么这些参数这样定：

- **不用 CMake**：这台机器没有 CMake/make/ninja。所以 `build.py` 直接按上游
  `tests/CMakeLists.txt` 的命令逐条构造编译命令，两边配置完全一致——差别只在
  被测量的那个变量。用一个跑不起来的构建系统写实验协议，等于给评委一个无法
  复现的方法。
- **`-j8` 而不是用满 20 核**：63 个单元的尾巴效应会让墙上时间变成调度产物。
  固定的绝对值更差，但两臂可比。
- **`-O0`**：上游 CI 就是不带优化构建；`-O2` 下优化器会盖住头文件成本。
- **干净构建**：增量构建会隐藏头文件成本，而头文件成本正是被测对象。

## 二、主实验：完整构建前后对照

`run_experiment.py` 做四件事：扫描一次（拿到估算）→ 按估算实施 PCH →
两臂各 5 次干净构建 → 逐套件跑完 63 个测试二进制。

实测结果（`results/experiment-20261017.md`，含逐轮原始秒数）：

| 指标 | 基线 | 加 PCH | 结果 |
|---|---:|---:|---|
| 完整构建墙上时间（中位数） | 43.2 s | 40.1 s | **节省 7.1%** |
| 编译 CPU 合计（中位数） | 292 s | 259 s | **节省 11.4%** |
| 测试断言（63 套件） | 4,264,414 | 4,264,414 | **完全一致** |

**估算与实测分开写，这是这份实验最重要的一条纪律：**

| 来源 | 量纲 | 数值 |
|---|---|---:|
| 估算 | 行数 | 消掉 9,919,690 行头文件解析量（占全项目 91.2%） |
| 估算 | 覆盖率 | 63/63 个编译单元（模型看不见配置宏，见下） |
| 实测 | 编译 CPU | 11.4% |
| 实测 | 墙上时间 | 7.1% |

从这两行反推：这个工程里**头文件解析约占编译 CPU 的 17%**（推算，前提是各单元
成本均匀）。所以「估算 91%」落地成「实测 11%」不是模型错了，是两个量本来不同：
91% 是头文件这一层的可压缩比例，11% 是整条编译流水线的可压缩比例。
把估算当秒数引用是错的，本项目在任何文档里都不这么用。

**门禁不是走过场**：第一版实验里 PCH 让两个套件的断言数变了（`unit-assert_macro`、
`unit-diagnostics`），原因是它们 `#define JSON_ASSERT` / `JSON_DIAGNOSTICS` 之后才
包含 `json.hpp`——PCH 把宏状态固化了。门禁抓到后，改成「凡在 include 之前改配置宏
的单元一律不用 PCH」（16/63），覆盖率从 63 降到 47，**收益也跟着降**。
这一步是 PCH 的通用约束，不是本工具的缺陷，但它必须写进报告而不是悄悄跳过。

PCH 真的生效了吗？`results/experiment-*.md` 的 4.1 节逐单元对照：
覆盖单元的编译时间中位数 −21.6%，未覆盖单元 −0.7%（它们是实验内置的对照组）。
两组同时符合预期，说明加速来自 PCH，而不是「这一轮机器比较闲」。

## 三、对照实验：两种推荐策略，同一测量协议

`control.py` 让两个策略解同一道题：找出「注释掉一个 include 后仍能编译、
测试断言数不变、且编译时间真的下降」的改动。每试一个候选的代价是
改一行 → 编译该单元 → 链接 → 跑该单元测试 → 比对断言数。

- **经验法则**：按「被多少个单元 include」排序，最常被 include 的先试；
- **HeavyHeader**：按 `scan` 给出的顺序试（候选空间 + 排序都是它自己的）。

### 测量协议（v2，2026-10-17 修正）

两个测量缺陷曾让这个实验给出过错的结论，都写在这里而不是悄悄改掉：

1. **并行基线与串行试验不可比**。第一版用 8 路并行测基线、单次串行测试验，
   基线被 CPU 争抢抬高约 25%，于是「编译成功」的候选看起来都有 13-21% 收益。
   串行复测那三个候选：+0.4% / -1.1% / -0.1%。
   **改法**：基线一律 `jobs=1`，与试验同机器状态。
2. **阈值落在噪声里**。第一版把 2% 写死为「有效」线。A/A 空对照（编译
   *未修改*的文件，真实收益恒为 0）显示这台机器单次编译就能飘 2-4%。
   **改法**：阈值取 `max(2%, A/A 空对照中观察到的最大 |Δ|)`，每次运行现场量。

### 候选排序的缺陷与修复（2026-10-17）

第一版工具提出的 5 个候选**全部编译失败**。根因不在指标，在两处结构性错误：

| 缺陷 | 后果 | 修复 |
|---|---|---|
| 用法判定只看候选头**自己**那段文本 | `TEST_CASE` 在 `doctest.h` 里，不在 `doctest_compatibility.h` 里，于是「没人用」 | 判定覆盖**独占闭包**（删掉这行后不再被解析的那批头），并指出符号由哪个文件提供 |
| 按「全项目可省行数」排序 | 收益最大的头正是最不可能可删的头，它排第一 | 先按「能不能采纳」分层，层内按**本单元**预计省下的秒数排 |
| 候选池排除系统头 | 工具永远看不见 `#include <iostream>` 这类改动，而实验里真实存在的改动全在这一类 | 编辑动作发生在自己的源文件里，系统头同样可提议；`kind` 退化为标签 |

`rank_check.py` 做零次构建试验的回顾性检验：拿已实测的 17 个结局当答案，
看新排序把好改动和坏改动分开到什么程度。结果：13 个已知失败候选**全部**
被判为「正在使用」，已知可删的 `unit-bjdata/iostream` 升到第 3 名。

### 结果

见 `results/control-20261017.md`（协议版本、A/A 噪声底、两臂逐次结局都在里面）。
关于「优势是否成立」，诚实的答案是**分层**的：

- **成立**：回答「成本集中在哪、该做 PCH 还是该删 include」——主实验实测 −11.4%；
- **分情况**：回答「这一行能不能删」——排序已修（见上表与回顾性检验），
  但最终判定权在 `verify`：它真的注释掉那一行、重编、测时间。扫描排序的
  意义是少花构建试验，不是替代构建试验。

## 三之五、同类竞品真实对比（`competitor.py`）

评审问「与现有工具相比优势是否成立」。这个问题只有跑一个真竞品才算回答，
所以 `competitor.py` 把 **clang-include-cleaner（LLVM 23.1.3，本机 LLVM 工具链自带）**
拉到同一工程、同一任务上：找出可删除的 include。它是这个问题的业内标准做法，
用真 clang AST 判定，和本工具的文本启发式正好构成对照。

实测（`results/competitor-20261018.md`，64 个单元）：

| | clang-include-cleaner | HeavyHeader（`scan --probe`） |
|---|---|---|
| 删除类建议 | **0 条** | 222 个候选全部探针实测 |
| 补充类建议 | **101 条**（63 个单元） | 0 条（我们不假装做 AST 级分析） |
| 删除后仍能编译 | —（不编译验证） | 35 个 |
| 实测变快 | — | **1 个**：`unit-windows_h` 去掉 `windows.h`，1620 ms → 950 ms（−41.4%） |
| 墙钟 | 90.3 s（纯分析） | 55 s 扫描 + 303 s 探针 |
| 分析失败 | 1 个单元 | 0 |

**两条必须一起读的诚实事实：**

1. 竞品分析失败的那一个单元是 `unit-windows_h`——**正是我们实测到 −41.4% 的那个**。
   所以「竞品 0 条删除建议」是在少了这一个单元的前提下成立的，
   「竞品没发现它」里有一部分是「竞品没能看这个单元」，不全是「竞品不关心成本」。
2. 竞品给出了 101 条我们给不出的补充建议（`nlohmann/json_fwd.hpp` 之类）。
   它在正常工作，只是在回答另一个问题：它管**正确性**，我们管**成本**。

结论因此是互补而非胜出：把竞品输出当成本输入、把我们的成本排序当竞品的优先级，
是更现实的组合用法。单方面宣布「我们赢了」会同时歪曲两边。

## 三之点五、删除建议决策层实测（`decision_check.py`）

评审要求「每次迭代都附带实际证据」。这一节对应第 3 轮迭代：把删除建议从
「疑似未使用」的可能性措辞，升级为**明确结论 + 三维度取舍依据 + 可复现实测**。
`decision_check.py` 在同一工程、同一编译器上回答三个问题。

实测（`results/decision-20261018.md`，222 个候选全部真实编译）：

| 结论 | 数量 | 含义 |
|---|---:|---|
| 建议删除 | **1** | 编译通过 **且** 耗时下降超过 2% 噪声线 |
| 保留 | 187 | 编译器已否决（编译不过）或定位不到该注释哪一行 |
| 需人工判断 | 34 | 编译可行但收益在噪声内；全部给出倾向（偏留 34） |

**222/222 个候选都有明确结论，没有一条停留在「疑似」。**

唯一一条「建议删除」的三个维度全部实测：

| 维度 | 数据 |
|---|---|
| 编译时间 | 1610 ms → 910 ms（**−43.5%**，每侧 3 次取最小） |
| 编译器内存（GGC 自报） | 301,052 kB → 168,960 kB（−43.9%） |
| 目标文件体积（完整编译实测） | 63,004 B → 62,972 B（−32 B，−0.05%） |
| 复现 | `heavyheader scan <root> --compiler g++ --compile-commands <db> --probe` |

体积那一行是个有信息量的阴性结果：**收益全部在编译时间侧，产物体积几乎不变**——
这类「哪个维度没有收益」的数据和正向收益一样必须实测，不能省略。

与竞品交叉核对（同工程同单元）：我们这 1 条倾向删除的 include，竞品恰好
**没能分析那个单元**（它自己失败）；竞品 0 条删除建议、101 条补充建议。
结论不变：精度上落后（AST vs 文本），收益验证上竞品无对应能力，两者互补。

### 这一轮抓到的两个真 bug（都写进 `docs/methodology.md`）

1. **源文件被传了两次**（影响此前全部计量）：compile_commands 的 `-c foo.cpp`
   留在 flags 里，驱动又追加一次源文件，GCC 安静地编译两遍、打出两条 TOTAL，
   读取方只取第一条。扫描/探针/基线的计时与 include 树全部建立在错误命令上。
   症状是「移除后 0 ms / 节省 100%」——TOTAL 丢失后的 0.0 被读成完美优化。
   修复 + 回归测试见 `tests/test_scanner.py`、`tests/test_drivers.py`。
   副作用：扫描 54.1 s → 32.2 s、探针 426 s → 213 s（本来就不用编两遍）。
2. **GCC/MinGW 计时损坏没有回退**：`-ftime-report` 对某些头文件打印不可能的
   秒数，sanity check 丢弃 TOTAL 后 `total_wall_seconds()` 返回 0.0。
   现在回退到驱动实测墙钟，并在报告里标明计时口径。

## 四、复现

```bash
cd heavyheader
python experiments/fetch.py            # 下载 + 校验固定快照（约 400 MB 语料）
python experiments/run_experiment.py   # 主实验：约 9 分钟
python experiments/control.py          # 对照实验：约 10 分钟（含 A/A 空对照）
python experiments/rank_check.py       # 回顾性检验：一次扫描 + 零次构建试验
python experiments/competitor.py       # 竞品对比：约 8 分钟（clang-include-cleaner）
python experiments/decision_check.py   # 决策层实测：约 6 分钟（结论覆盖 + 维度 + 竞品交叉）
python experiments/run_experiment.py --render-only experiments/results/experiment-YYYYMMDD.json
                                       # 只重渲染 Markdown，不重跑构建
```

产物：

| 文件 | 内容 |
|---|---|
| `results/experiment-*.json` | 全部原始数据：每轮墙上时间、每单元 CPU、逐套件断言数 |
| `results/experiment-*.md` | 人类可读报告（由上者渲染，`--render-only` 可重生成） |
| `results/control-*.json` / `.md` | 对照实验的 A/A 噪声底、两臂逐次试验记录与判读 |
| `results/rank-check-*.json` / `.md` | 回顾性检验：新排序 vs 已实测的 17 个结局 |
| `results/competitor-*.json` / `.md` | 竞品对比：clang-include-cleaner vs 本工具，同工程同任务 |
| `results/decision-*.json` / `.md` | 决策层实测：222 个候选的明确结论、三维度数据、竞品交叉核对 |
| `_work/` | 拉取的源码、语料、对象文件（已 gitignore，可随时重建） |

## 五、失败案例与局限（如实写）

1. **探针阶段曾给出假编译失败**（已修，`b1e8902`）：它原来用 `ScanOptions` 级的
   参数重建单元，把 `compile_commands.json` 里每个单元自己的 `-I` 全丢了，
   编译器找不到项目头文件，于是每个候选都报「移除后编译失败」——结论看起来是
   「这里没有可删的」，实际是「我们问错了问题」。这个 bug 之所以能活过测试套队，
   是因为兜底路径足够合理：不崩，只是答错。现在 `TranslationUnit.compile_options`
   记录每个单元真实的编译参数。
2. **候选排序曾全面失败**（第三节）：工具排在最前的 5 个候选全部编译失败。
   已修（判定覆盖独占闭包 + 排序改为「可采纳性优先」），修复由
   `rank_check.py` 的零次试验检验背书；但**修复只改善排序，不改变一个事实**：
   「这行能不能删」的最终判定只能来自真的编译一次。
2. **16/63 个单元无法用 PCH**：它们在 include 之前 `#define` 了配置宏，改的是头文件
   语义。第一版实验没排除它们，被门禁抓出 15 条断言差异——那次「加速」是假的。
3. **单机、单编译器、单工程**：绝对值不可迁移，可迁移的只有量级与结论方向。
4. **测量偏差毁过一次结论**：第一版对照实验的「经验法则 3/12」是并行基线与串行
   试验的产物。A/A 空对照现在内建在 `control.py` 里，每次运行现场量噪声底，
   阈值跟着走。
5. **不测维护成本**：PCH 的代价是「改到 PCH 里的头会触发全量重建」，本实验没测它。
6. **对照实验是脚本代理，不是真人研究**：它衡量试验轮次与试验墙钟，不衡量人的
   思考时间。任何「省了多久人工」的说法都属估算，不与实测并列。
7. **源文件曾被传了两次**（2026-10-18 修复，见「三之点五」）：`compile_commands`
   模式下每个编译命令都多带一份源文件，GCC 静默编译两遍。修复前的一切
   compile_commands 模式计量（含早期探针数字）都建立在这条错误命令上；
   本 README 中 2026-10-18 的数字均为修复后重跑所得。
