# 前向声明实测闭环：机制跑通了，候选用完了

数据冻结日：2026-10-27。对应提交：`forward-verify` 子命令 +
`attrib/fwdverify.py`。复现：`python experiments/fwd_verify_probe.py`
（原始数据 `experiments/_work/fwd-verify/probe.json`）。

## 一句话结论

`forward-verify` 把「这条 include 能不能换成前向声明」从**正则判断**变成了
**编译器 + 汇编指纹的裁决**，机制在合成语料上闭环成立（301.7 ms → 41.9 ms，
省 86.1%，指纹一致）。但**三个真实语料上一条候选都没有**——所以这次交付的是
「把建议钉死在证据上」的能力，不是「前向声明能省多少」的数字。

## 真实语料：候选数

| 语料 | 成功编译的单元 | 前向声明候选 | 含阻塞类型 |
|---|---:|---:|---:|
| nlohmann/json v3.11.3（既有 63 TU 语料） | 57 | **0** | 0 |
| spdlog v1.14.1（整棵树） | 3 | **0** | 0 |
| `benchmarks/cases/demo` | 2 | **0** | 0 |

两个必须一起读的限制：

- spdlog 整棵树有 12 个 `.cpp`，**只有 3 个编过**——`tests/` 依赖 Catch2，
  而它是 CMake 构建时 `FetchContent` 拉下来的，不在 tarball 里。所以这行的
  「0 候选」只覆盖那 3 个单元，**不能外推到整棵树**。
- 候选数 0 不是工具出错：同一套判定在合成语料上找得出候选（见下节）。

### 为什么是 0

文本判据要求「这个头里的每一个类，在单元里**只**以指针/引用出现」。这条在现代
C++ 里几乎立刻被打破：

- `std::shared_ptr<Widget>`、`std::unique_ptr<Widget>`、`std::vector<Widget>`
  这类模板实参都不匹配「名字后面跟 `*` 或 `&`」，于是整条 include 被判成
  「需要完整定义」；
- 真实的 `.cpp` 里最常见的写法是 `auto x = factory();`，**名字根本不出现**。

这不是新发现的缺陷，是这条规则一直以来的形状（`forward.py` 的 docstring 就写着
「deliberately conservative」）。以前没有实测路径，保守只是态度；现在有一条能
把候选变成结论的路，保守的代价第一次被量出来：**在真实代码上它几乎不产出候选**。

顺带一个正面结果：`forward.py` 的保守方向是对的。给同一个头加一个
`std::shared_ptr<ui::Widget>` 参数的单元后，候选数**没有增加**（1 → 1）——
那个单元被判为需要完整类型。这个判定是正确的：`shared_ptr` 在函数定义里销毁时
要实例化删除器，那一刻 `Widget` 必须完整。

## 合成语料：机制闭环

刻意造成前向声明收益最高的经典形状：`widget.h` 里只有一个类，并带一个 1,500 行、
依赖 `<string>/<vector>/<map>/<algorithm>` 的负载头；单元只把类当指针用。

| | 数值 |
|---|---|
| 候选 | 1（`ui::Widget`） |
| 原文件 | 301.7 ms |
| 换成前向声明后 | 41.9 ms |
| 节省 | 259.8 ms（**86.1%**） |
| 汇编指纹 | **一致**（`-S`/`-g0` 比对，`--check-codegen` 默认开） |
| 结论档 | 已证等价 |
| 写进源码的声明 | `namespace ui { class Widget; }` |

每侧编译 2 次取最小值，墙钟口径（与 `verify` 相同）。

**这个 86.1% 不能当效能证据。** 合成语料的负载头是我为了造出信号而写的，
真实工程里「一个头只有一个类 + 1,500 行与它无关的负载」这种形状本身就是前向
声明要解决的病灶，拿它算全项目收益率等于自问自答。它的用途只有一个：证明
「换上去 → 编译 → 比指纹 → 分档」这条链每一环都真的走通了。

## 三处设计上的取舍

1. **只测 TU，不测头。** 候选来自 `scan.forward_decl`，它只遍历编译单元的直接
   include。头文件里的 include 理论上才是前向声明的主战场，但改公共头要走
   `verify` 那套「原地改 + finally 还原」的路子（副本在临时目录里根本不会被
   include 解析找到），风险高一个量级。这一版没做，是取舍不是遗漏。
2. **补丁写在原位置。** 前向声明插在被注释掉的 `#include` 那一行下面，而不是
   文件头——写在 `#ifdef` 里的 include 换出来的声明也应该受同一个 `#ifdef`
   管辖，挪到文件头会悄悄改变可见性。
3. **失败有独立档位。** 「编不过」是结论（这个单元真的需要完整类型）；
   「同一头里还有需要完整定义的类型」是 *needs-split*（先拆头才能谈前向声明）；
   「汇编指纹取不到」只到 *compiles-only*。三者在报告里分开计数，不合并成
   「失败」。

## 与既有口径的关系

- 与 `scan --forward-decl` 的关系：那条给**行数级候选**，这条给**秒级结论**。
  两条命令刻意分开，合在一起会让文本判据借实测的可信度。
- 噪声地板沿用 `attrib/advice.py` 的 20 ms。收益落在噪声内降为 *equivalent*
  （程序没变已证，值不值得改未证），不计入可报收益。
- 不换算行数与秒，不把合成语料的百分比外推到真实工程。

## 下一步（如果要提高召回）

按性价比排序，都还没做：

1. **把智能指针当指针看**：`std::shared_ptr<T>` / `unique_ptr<T>` 在*声明*位置
   只需要 `T` 的前向声明（销毁点除外）。这一条能把真实语料的候选数从 0 拉起来，
   但需要区分「声明」与「销毁」位置，判据比现在复杂一个量级。
2. **头文件级候选**：前向声明的主战场。要复用 `verify` 的原地改+还原机制。
3. **记录 `auto` 推导出的类型**：需要 AST，超出当前纯文本架构。
