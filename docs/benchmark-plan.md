# 同任务基准计划（预注册）

> 目的：用**同一份工程、同一组输入、同一台机器**，回答「HeavyHeader 是否比现有工具更值得用」。
> 本文件在跑测之前写定，避免看到结果再挑指标。阈值留空，跑完基线后填——**不预设漂亮数字**。

## 1. 三个门槛（不过就不扩张）

| 门槛 | 问题 | 通过条件 | 不通过时怎么办 |
|---|---|---|---|
| **G1 公平对照** | 在至少一个真实工程上，是否比现有工具多出可复现的新增价值？ | 见 §6 的 G1 判定 | 缩窄定位，或只做现有工具的治理集成层 |
| **G2 闭环成立** | 能否在预定义测试集上找到可复现的有效优化？ | 见 §6 的 G2 判定 | 不再宣传「自动/可验证优化」 |
| **G3 治理成立** | CI 门禁能否以可接受成本发现回归且误报可控？ | 见 §6 的 G3 判定 | 不把门禁当主卖点 |

## 2. 预注册：这些变量在跑测期间不得改

| 变量 | 固定方式 |
|---|---|
| 源码版本 | 每个工程锁定 commit SHA，写进结果文件 |
| 编译器 | GCC / Clang / MSVC 各自版本号完整记录（`--version` 原文） |
| 编译参数 | 从 `compile_commands.json` 或工程自带预设原样取，不手工优化 |
| 构建类型 | 统一 Debug / RelWithDebInfo 各一轮，不混用 |
| 缓存状态 | 冷缓存（先 `make clean` / 删 build 目录）；ccache 显式关闭 |
| 机器状态 | 同一台机器、接电源、后台无其他负载；记录 CPU 型号与核数 |
| 并行度 | 对比耗时统一 `-j1`；另跑一轮默认并行仅作参考，不进判定 |
| 重复次数 | 每项 ≥ 3 次，取中位数与离散度；A/A 对照另跑 3 次 |
| 顺序 | 每轮开始前重置缓存与产物；工具顺序随机化，避免热机偏差 |
| 排除规则 | 统一排除仓库内 vendored 测试框架（`tests/thirdparty/**`、`vendor/**`、`external/**`），并把规则写进结果；不得只对一方排除 |

## 3. 基准工程（3 个，类型必须不同）

| 工程 | 类型 | 选择理由 | 已知风险 |
|---|---|---|---|
| nlohmann/json | 单头模板库 | 模板与头文件密集，现有基准可重复性可验证 | 单头结构可能不代表多模块工程 |
| fmt | 模板 + 多 TU 库 | 观察不同模板结构下的热点排序差异 | 规模偏小，耗时差可能落入噪声 |
| 一个中型 CMake 工程（含测试与 CI） | 真实业务工程 | 检验接入难度、失败处理与治理价值 | 待选定；需能在本机完整构建 |

> 三个工程都是候选，不预设「一定适合」。跑完接入步骤后若某个工程无法在 30 分钟内构建成功，
> 记录失败原因并替换，不硬凑。

## 4. 工具映射（按工程能力选，不强求每个工具做全部任务）

| 工程 | 对照工具 | 对照任务 |
|---|---|---|
| Clang 可构建的工程 | ClangBuildAnalyzer + 原生 `-ftime-trace` | 热点发现、采集成本、Top-10 一致性 |
| MSVC 可构建的工程 | C++ Build Insights（`vcperf` + WPA） | 头文件耗时、PCH 建议、额外治理步骤 |
| 任一工程 | IWYU 或 Include Cleaner | include 清理的候选数、编译成功率 |
| 任一工程 | deheader | 删除后重编译的候选数与耗时 |
| 任一工程 | cpp-dependencies、include-gardener | 依赖结构分析是否已够用（若可用） |
| 全部工程 | HeavyHeader `scan/verify/gate/compare` | 完整闭环 |

## 5. 每个工具要记的数据（8 类，缺一类即该轮无效）

| # | 类别 | 具体字段 |
|---|---|---|
| 1 | 首次接入 | 安装耗时、配置步骤数、失败原因、是否需要改构建文件 |
| 2 | 数据采集 | 墙钟、CPU 时间、峰值内存、额外磁盘占用 |
| 3 | 热点发现 | Top-10 列表（原样保存）、排序依据、是否可解释 |
| 4 | 优化建议 | 候选数、可编译比例、人工审核分钟数 |
| 5 | 实际效果 | 干净构建与增量构建的墙钟/CPU，各 3 次中位数 |
| 6 | 测量可信度 | 重复次数、A/A 差值、噪声底、失败案例 |
| 7 | CI 集成 | 配置行数、单次运行开销、误报数、漏报数 |
| 8 | 跨平台 | GCC/Clang/MSVC 实际跑通情况与差异 |

## 6. 判定规则（阈值在基线跑完后填写）

### G1 公平对照

- 必答：在**热点发现**上，我们的 Top-10 与 CBA/Build Insights 的一致率是多少？
  低于某个值说明我们的发现能力更差，必须承认。
  **实测（2026-10-18，nlohmann/json 25 TU，同编译器、同候选规则、同构口径）**：
  Top-10 重合 7/10、Spearman ρ ≈ 0.68；按 CBA 发布口径（含子头）为 5/10、ρ ≈ 0.42。
  结论：中度一致，**不支持「我们更准」**；详见 `docs/benchmark-report.md` §8。
- 必答：在**验证环节**，是否提供了对手完全没有的信息（删后 Δ时间/Δ内存/Δ体积）？
- 必答：从「拿到工程」到「得出第一条可信结论」的人工时间，是否不高于对手？
- 阈值：`____`（跑完基线后填，且需两名评审可复核）

### G2 闭环成立（2026-10-18 修订：拆成三个子问题）

旧版只有一个「可采纳率」。它把两件完全不同的事压成了一个 0：
「这个工程没有值得删的东西」（工程的属性）和「有值得删的东西时工具也
找不出来」（工具的缺陷）。一个 0 分不开它们，所以它既不能指导改进，
也不能对外声明。修订后：

- **G2-1 可行性**：推荐列表里有多少条**能编译通过**。对照臂是把可行性
  闸门关掉、纯粹按收益大小取前 K 条。两臂之差才说明闸门有没有用。
- **G2-2 天然收益可采纳率**：工程**原本就有**的候选里，有多少条实测省时
  超过噪声线并通过复测。
- **G2-3 召回**：往真实工程注入已知可删、且确实昂贵的 include，工具能否
  把它找出来（在列表里、排第几）并实测证实。注入的 include 是人造的，
  编译与测量不是——所以这一组只能回答「有收益时找不找得到」，
  不能回答「这个工程有多少优化空间」。

测量协议同时修订：候选改到**头文件级**后，一次改动影响多个单元，判定
必须用**聚合 + 交替**口径，阈值 `AGGREGATE_NOISE_FLOOR = 1%`（由
`experiments/g2_interleaved.py` 的 A/A 实测标定：0.644% / 0.245%）。
TU 级候选仍用单单元口径 + `TIME_NOISE_FLOOR = 2%`——两者分母不同，
混用会放松或收紧标准，都不对。

- 阈值：G2-1 要求闸门臂编译通过率显著高于无闸门臂；
  G2-2 不设通过线（先测出真实收益的量级，再决定要不要设）；
  G2-3 要求注入项进入候选列表且能被实测证实。

### G4 工程开销（本轮新增）

- 判据：同任务下，扫描墙钟 ÷ 纯编译墙钟 ≤ **1.5×**；峰值内存 ≤ **100 MB**；
  同输入三次的归因行数与 Top-10 完全一致；至少两种编译器可运行。
- 为什么设这三个数：超过 1.5× 意味着用户为分析多付一半等待，CI 会关掉它；
  内存超过 100 MB 会挤占 CI 容器；不确定的排行榜不能用来对比基线。
- 实测（2026-10-18）：1.15×（g++）/ 1.20×（clang++），峰值 9.2 MB，三次全一致。
  **成立**。MSVC 未测（`reg.exe` 被策略拦截）。

### G3 治理成立

- 主指标：注入一次已知成本回归，门禁是否稳定发现（≥3/3）。
- 反指标：无回归时误报次数（A/A 对照下必须为 0）。
- 成本：单次门禁运行时间与 CI 预算的比值。
- 阈值：`____`

## 7. 产出物

- 原始数据：`experiments/results/bench-<工程>-<日期>.json`（每个工具一份，字段固定）。
- 汇总：`docs/benchmark-report.md`，含每项的中位数、离散度、失败案例。
- 失败也要写：无法接入、跑不动、结果矛盾，都是结论的一部分。

## 8. 已知会干扰结论的因素（先写下来，跑完对照）

1. **扫描期诊断开销**：`-H` + `-ftime-report` 有额外开销；`--full-compile` 还会为每个单元
   多链接一次（已实测导致 1.72× 高估，见 `incremental-tax-20261018.json`）。
2. **Windows 计时**：`-ftime-report` 的 TOTAL 是 CPU 时间，与墙钟可差 30 倍；
   所有「等待时间」类指标必须用驱动实测墙钟（已修）。
3. **工程规模**：小工程的耗时差容易落入噪声，不能用来证明「更快」。
4. **对照工具的默认配置**：不得为对手调差参数，也不得为自己调优参数；一律用默认。
5. **人工时间的测量**：由同一人按同一脚本操作，记录分钟数，避免「我觉得更快」。

## 9. 执行状态（2026-10-18）

- 阶段 0（噪声底与确定性）已完成：见 `docs/benchmark-report.md`。
  结论：结构指标确定；单 TU 计时噪声底 1.58%；扫描开销 1.17×。
- G1 **部分通过**：ClangBuildAnalyzer 侧已跑通并完成同构对照（7/10、ρ 0.68）；
  微软 Build Insights 因 `reg.exe` 被策略拦截仍不可用，IWYU 未构建。
- G2 **成立（有限），2026-10-18 重做**：候选生成扩到头文件级 + 可行性闸门，
  测量改成交替协议（聚合 A/A 2.005% → 0.644%）。三个工程：doctest 1/5
  （删 `prelude.h` 的 `<unordered_set>`，24 单元全通过、−3.01%、复测通过）；
  json 0/5、zlib 0/5，两处闸门开 0 条；注入-召回 2/2（两遍都过线）。
  排序另换实测成本模型（`--cost-model trace`，开销 1.71×）：doctest 上 Top-1
  由「删了编译不过」换成「唯一可采纳的那条」。
  按预注册规则，仍**不把「自动优化」当卖点**——三个工程里两个是 0/5。
- G3 **成立（限归因行数型回归）**：检出 3/3、误报 0、单次 3.38 s。
- G4 **成立**：开销 1.15–1.20×、峰值 9.2 MB、确定性成立。
- 本阶段发现并修复一个会污染所有对照的缺陷：Top-10 排序受哈希随机化影响而不稳定。

## 10. 执行顺序

1. 选定第三个工程，锁定三个工程的 commit。
2. 先跑 A/A 对照，确定噪声底（这一步不通过，后面所有差异都不可信）。
3. 按 §4 逐工具采集，填写 §5 的八类数据。
4. 填 §6 阈值，出 `docs/benchmark-report.md`。
5. 按 §1 的三个门槛决定产品叙事：过哪个说哪个，不过的明确不说。
