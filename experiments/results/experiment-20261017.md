# 竞赛实验：真实工程的完整构建前后对照

> 本文件由 `experiments/run_experiment.py` 生成，请勿手改。
> 全部数字可用文末命令在同一台机器上复现。

## 0. 一句话结论

在 **nlohmann/json v3.11.3** 的测试树上，HeavyHeader 一次扫描（55.8 s）指出「5 个头文件构成 PCH 候选、覆盖 63/63 个编译单元（估算）」，按此实施后**完整构建**墙上时间中位数 43.2 s → 40.1 s（节省 7.1%），编译 CPU 时间 292 s → 259 s（节省 11.4%），63 个测试套件的断言数逐个与基线一致。

估算列出的候选中，`json.hpp` 的传递闭包已经包含其余几个（它们本来就在 json.hpp 里），所以实际 PCH 只需 `json.hpp` + `doctest.h` 两个条目即可覆盖估算的全部集合——这是闭包关系，不是遗漏。

注意这里有**两个覆盖率**：估算说 63/63 可用，实际只有 **47/63** 可用（其余单元改了头文件配置宏）。差异是模型看不见的，报告不藏。

## 1. 实验设置（固定项）

| 项 | 值 |
|---|---|
| 工程 | nlohmann/json `v3.11.3`（源码 SHA-256 `0d8ef5af7f9794e3…`） |
| 编译器 | `g++ (x86_64-win32-seh-rev1, Built by MinGW-Builds project) 16.2.0` |
| 编译参数 | `-std=c++11 -O0 -DDOCTEST_CONFIG_SUPER_FAST_ASSERTS -DJSON_TEST_KEEP_MACROS -DJSON_TEST_USING_MULTIPLE_HEADERS=0` |
| 头文件搜索路径 | `include tests tests/thirdparty/doctest tests/src` |
| 并行度 | `-j8`（固定，不用全部核心） |
| 重复次数 | 每臂 5 次**干净**构建（每次清空目标目录） |
| 编译单元 | 63 个测试单元 + 1 个共享 main |
| 正确性门禁 | 每个测试二进制单独运行，逐套件比对断言通过/失败数 |
| 噪声阈值 | 变化 < 2% 记为「无变化」 |
| 机器 | Intel64 Family 6 Model 183 Stepping 1, GenuineIntel / Windows 11 / Python 3.13.14 |

为什么固定 `-j8` 而不是用满 20 核：63 个单元的尾巴效应会让墙上时间变成
调度产物；固定并行度的绝对值更差，但两臂可比。为什么 `-O0`：上游 CI 就是
不带优化构建，`-O2` 下优化器会盖住头文件成本。

| 墙上时间最小值 | 42.52 s | 39.63 s | — | — |

## 3. 估算 vs 实测（两个数，不合并）

| 来源 | 量纲 | 数值 | 含义 |
|---|---|---:|---|
| HeavyHeader 估算 | 行数 | 9,919,690 行 | PCH 覆盖后可少解析的头文件文本量（已扣掉一次性构建） |
| HeavyHeader 估算 | 占比 | 91.2% | 占全项目头文件解析量的比例——这是**上限**，不是秒数 |
| 实测 | 墙上时间 | 7.1% | 完整构建实际省下的比例 |
| 实测 | 编译 CPU | 11.4% | 去掉链接与调度后的真实压缩量 |

**为什么两个数不一样，而且实测更小**：估算给出的是「头文件解析量中可被 PCH 消掉的比例」，实测给出的是「完整构建墙上时间里省掉的比例」。两者不是同一个量：估算按 63/63 个单元都可用 PCH 计算，实际只有 47/63 个可用（另外 16 个改了配置宏）；而头文件解析本身也只是编译时间的一部分，模板实例化、代码生成、链接与进程启动都不随头文件变化。

把两个数相除可以反推出「头文件解析占编译时间的比例」，但这是**推算**，
不是实测，前提是假设各单元成本均匀、且模型的行数占比等于工作量占比：

> 推算头文件解析占比 ≈ 实测编译 CPU 节省 11.4% ÷ (估算 91.2% × 实际覆盖率 75%) ≈ **17%**

也就是说：在这台机器、这个工程上，头文件解析大约占编译 CPU 的 17%，其余是模板实例化与代码生成。PCH 只能压缩前者——这解释了为什么「估算 91%」落地成实测 11%（编译 CPU）/ 7%（墙上时间）。把估算值当秒数引用是错的，本项目在任何文档里都不这么用。

## 4. 正确性门禁

- 对比套件数：**63**
- 断言通过：基线 **4,264,414** / PCH **4,264,414**
- 结论：**逐个一致，构建加速未改变语义**

## 4.1 PCH 真的生效了吗（逐单元对照）

「整体变快」必须能分解到具体单元，否则可能只是环境抖动。下表每个单元取各臂多次构建的**最小值**：覆盖到的单元应明显变快，未覆盖的单元应基本不动——后者是这次实验内置的对照组。

| 单元 | 用了 PCH | 基线 (s) | 加 PCH (s) | 单单元节省 |
|---|---|---:|---:|---:|
| `unit-type_traits` | 是 | 1.55 | 0.84 | 45.5% |
| `unit-byte_container_with_subtype` | 是 | 1.84 | 1.00 | 45.5% |
| `unit-noexcept` | 是 | 1.54 | 0.89 | 42.6% |
| `unit-ordered_map` | 是 | 1.98 | 1.29 | 35.0% |
| `unit-to_chars` | 是 | 2.04 | 1.34 | 34.2% |
| `unit-concepts` | 是 | 2.02 | 1.33 | 34.2% |
| `unit-json_pointer` | 否（配置宏） | 5.30 | 5.29 | +0.2% |
| `unit-conversions` | 否（配置宏） | 12.65 | 12.67 | -0.2% |
| `unit-class_lexer` | 否（配置宏） | 1.75 | 1.76 | -0.3% |
| `unit-regression1` | 否（配置宏） | 13.06 | 13.02 | +0.3% |

覆盖单元的单单元节省中位数 **21.6%**，未覆盖单元 **-0.7%**（应接近 0——它们在两臂中采用完全相同的命令编译）。两组同时符合预期，说明加速来自 PCH 本身，而不是「这一轮机器比较闲」。

## 5. 一次扫描给出了什么

- 编译单元：**63** 个成功（失败 0 个）
- 依赖边：**41,408**，头文件解析量：**10,872,819** 行
- 成本候选（可能可移除的 include）：**147** 个
- 扫描自身耗时：**55.8 s**（一次性）

| 项目头 | 行数 | 归因行数（被重复解析的总量） | 触达 TU |
|---|---:|---:|---:|
| `tests/thirdparty/doctest/doctest.h` | 7,106 | 447,678 | 63 |
| `include/nlohmann/json.hpp` | 5,258 | 331,254 | 63 |
| `include/nlohmann/detail/input/binary_reader.hpp` | 3,009 | 189,567 | 63 |
| `include/nlohmann/thirdparty/hedley/hedley.hpp` | 2,045 | 128,835 | 63 |
| `include/nlohmann/detail/output/binary_writer.hpp` | 1,838 | 115,794 | 63 |

这张表就是「为什么是 PCH 而不是逐个删 include」的全部理由：头部那个头的归因行数是自身体积乘以 TU 数——删掉任何一个 TU 的 include 只省一份，把它放进 PCH 才一次省掉全部。

## 7. 局限（如实写）

1. **16/63** 个单元无法使用 PCH：它们在 `#include <nlohmann/json.hpp>` 之前 `#define` 了 `JSON_TESTS_PRIVATE` / `JSON_DIAGNOSTICS` / `JSON_ASSERT` 等配置宏，改的是头文件的**语义**。PCH 会把构建时的宏状态固化进去，这类单元只能用非 PCH 配置编译。这是 PCH 的通用约束（不是本工具的缺陷），代价是收益上限被压住。实验里这 16 个单元在**两个臂中都以同一方式**编译，因此不影响可比性。
2. 单机、单编译器、单工程。数字的可迁移性只到「量级」这一层，换机器或换 MSVC 后绝对值会变。
3. 墙上时间受磁盘缓存与系统负载影响；已用「每臂多次干净构建 + 取中位数」压制（本次每臂 5 次），但不足 2% 的差异仍判为无变化。
4. 本实验只测**编译时间**，不测开发者体验、不测 PCH 的维护代价（改到 PCH 里的头会触发全量重建）。
