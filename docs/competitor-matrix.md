# 竞品能力矩阵（含证据等级）

> 核实日期：2026-10-18。本文的目的不是证明 HeavyHeader 更好，而是**判断差异化是否真实存在**。
> 每个格子必须带证据等级；没有证据的格子一律写「尚未验证」，不得用推测填充。

## 0. 证据等级定义

| 标记 | 含义 | 判定标准 |
|---|---|---|
| **D** | 官方文档已证实 | 本轮实际取回官方文档/README 原文，能引用具体功能描述 |
| **C** | 源码已核验 | 读过实现代码，不只是文档声称 |
| **L** | 本地实验已证实 | 在本机跑过，有可复现命令与输出 |
| **?** | 尚未验证 | 只有传闻/印象，或本轮没查到一手来源 |

一张矩阵里如果 **L 很少**，说明差异化大多还停留在文档层面——这正是本文要暴露的。

## 1. 竞争四层地图

| 层 | 工具 | 与本项目的关系 |
|---|---|---|
| 直接竞品 | ClangBuildAnalyzer、MSVC C++ Build Insights、IWYU、Include Cleaner | 用户会拿来直接替代或对照 |
| 相邻工具 | cpp-dependencies、include-gardener、Header Hero、IncludeGuardian、deheader | 功能局部重叠，常被组合使用 |
| 替代方案 | ccache/sccache、distcc/IncrediBuild、FASTBuild、Bazel | 争夺同一笔「构建慢」预算，未必同类 |
| 隐性竞争者 | 用户自写脚本 + CI、什么都不做 | 最常见的「不采用」原因 |

### 2.1 这张表直接得出的三个结论

1. **「发现成本」我们没有优势可言**：ClangBuildAnalyzer 与 Build Insights 在逐头文件耗时、
   模板、代码生成上都有官方文档支撑，且数据来自编译器内省。继续把头文件排行榜当卖点是撞墙。
2. **「验证建议」目前只有 deheader 一个先例**：它做「删除后重编译」，但只给二值结论、
   不量化收益。我们的「量化删后收益 + 三态决策」在矩阵里没有对照项——**但『没有对照项』
   不等于『有价值』，只等于『还没人验证过』**。这是待验证假设，不是护城河。
3. **「治理」看似空白，实则被两件事侵蚀**：deheader 已有退出码门禁；IWYU 的
   `--error_always` 也能让 CI 失败。我们的门禁差异只在「按实测净收益判定」，
   而这一点尚未在真实 CI 上验证误报率。

## 3. 四维评估（候选差异化，不是既成事实）

| 维度 | 竞品现状 | 我们是否占优 | 证据 |
|---|---|---|---|
| A 发现成本 | CBA / Build Insights 已很强 | **否**，最多持平 | D |
| B 验证建议 | 仅 deheader 做重编译，且不量化 | 可能占优，**未对照** | L（单侧） |
| C 持续治理 | deheader 退出码、IWYU error_always | 可能占优，**未验证误报** | ? |
| D 低接入成本 | 多数需特定编译器或平台 | 可能占优（Python 零依赖 + 三编译器） | L（本机） |

**结论：A 不占优；B/C/D 是候选方向，全部缺少同任务对照。** 在补齐对照前，
任何「行业首创」「唯一」的说法都不成立。

## 5. 我们明确不声称

- 不声称「首个/唯一做头文件成本分析」——CBA、Build Insights 已覆盖。
- 不声称「建议最全」——IncludeGuardian 更全。
- 不声称「计时最准」——`-ftime-trace` 更细。
- 不声称「自动优化」——当前只有单条 include 级验证，且 R1/R2 未闭环。
- 不声称「CI 门禁行业首创」——deheader / IWYU 已有退出码级门禁。
