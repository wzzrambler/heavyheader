# 「阻断归因第二半」的需求实测：需求是 0，所以不做

数据冻结日：2026-10-27。语料：nlohmann/json v3.11.3（既有 63 TU 实验语料，
本次 57 个单元编译成功、15 个失败）——与 PCH / 前向声明两组实验同一份语料，
便于横向比较。

## 要判断的问题

路线图里有一条一直开着：

> **阻断归因（第一半）**：解析编译器报错 → 符号 / 位置 / 处置方向。
> **第二半（改一遍再编译、实测收益）未做。**

第一半已经在 `attrib/blockers.py` 里跑了很久：删掉 include 之后编译失败，
它把报错归因成「缺什么符号 + 该往哪个方向改」，其中一种方向是
**`FORWARD_DECLARE`**（符号是这个头的类型，且源码只把它当指针/引用用）。
第二半的意思是：**照这个方向真的改一遍、再编译、量收益**。

动手之前先问一个便宜的问题：这件事到底有多少个真实案例？如果归因到
`FORWARD_DECLARE` 的候选是 0，第二半就是给一个空集合写代码。

## 怎么量的

对 json 语料跑一次 `scan --probe-compile`：每条候选都真的注释掉、编译一次，
失败的交给 `blockers.attribute` 归因，然后数方向。

```bash
# 注意 -I 必须是绝对路径：-I 相对的是**当前目录**，不是扫描根。
# 在仓库根用相对路径写 -I include，57 个单元里会有 71 个以「找不到头」失败，
# 候选数只剩 2——一个看起来像「这个项目没什么可删」的空结论。
heavyheader scan experiments/_work/pch-verify-json/corpus \
  --compiler g++ --std c++11 --flag=-O0 \
  -D DOCTEST_CONFIG_SUPER_FAST_ASSERTS -D JSON_TEST_KEEP_MACROS \
  -D JSON_TEST_USING_MULTIPLE_HEADERS=0 \
  -I "$PWD/experiments/_work/pch-verify-json/corpus/include" \
  -I "$PWD/experiments/_work/pch-verify-json/corpus/tests" \
  -I "$PWD/experiments/_work/pch-verify-json/corpus/tests/thirdparty/doctest" \
  -I "$PWD/experiments/_work/pch-verify-json/corpus/tests/src" \
  --probe-compile -j 4 --format json -o probe.json
```

## 结果

127 条候选，其中 113 条被否决（`keep`），14 条留待人工判断。113 条的归因分布：

| 归因方向 | 条数 | 含义 |
|---|---:|---|
| 前向声明不适用 | 63 | 符号不是被删头（含其传递闭包）声明的类型；或那个头是系统/第三方头 |
| 与缺失声明无关 | 43 | 报错是语法、模板实例化一类，删除动作与它无关 |
| 前向声明不成立 | 7 | 确实需要完整类型（按值使用 / 成员访问 / sizeof） |
| **可前向声明（FORWARD_DECLARE）** | **0** | —— |

## 结论：不做

**0 条**。第二半要服务的对象在真实语料上不存在，做了就是给空集合写测量代码。

这个结果和前一项实验（`fwd-verify-20261027.md`）是同一个原因的两个切面：

- `forward-verify` 从**文本**找「只当指针用」的类，三个真实语料候选数都是 0；
- 阻断归因从**编译错误**找同一件事，json 上 113 条被否决的候选里也是 0。

两条独立入口都指向同一件事：**「头里的类只以指针/引用出现」这个条件在现代 C++
里几乎不成立**。`shared_ptr<Widget>` 这类模板实参不匹配判据，`auto` 连类型名
都不出现；而真正会被判成「缺类型」的，绝大多数是标准库符号（`std::vector`、
`std::cin`），C++ 语言规则根本不允许用户前置声明。

所以路线图里这一条**按证据关闭**，不是「没时间做」。要重新打开它，先得让
判据认识智能指针（区分声明点与销毁点），否则第二半永远没有输入。

## 顺带记录：一条会让人掉进去的坑

`-I` 相对的是**进程当前目录**，不是扫描根。README 主推的
`heavyheader scan ./proj -I ./proj/include` 是对的（两者都在当前目录下解析），
但把它拆成「在仓库根跑、`-I include`」就会全线找不到头——表现是
**71/72 个单元编译失败、候选只剩 2 条**。

**一句更正**：我最初把这件事记成「静默失败、报告读起来像项目很干净」，这是错的。
报告正文一直写着「编译单元：1 成功 / 71 失败」，stderr 也一直有
「N 个编译单元失败，数字可能偏低」。我没看见，是因为把 stdout 重定向到
`/dev/null` 只解析 JSON——读法问题，不是工具沉默。

所以它真正暴露的是**另一件事**：工具报了症状（编不过），没人报病因
（`-I` 的参照系是进程当前目录）。从 71 条「找不到头文件」倒推出「我的搜索路径
参照系错了」这一步，被留给了读者。已修：扫描开始时检查显式 `-I` 目录是否存在，
不存在就写进 `scan.warnings` 并说清参照系。
