# 路演问答（按实测数据准备）

> 这份文件的用途：把评审最可能问的问题，用**可复现的数字**回答。
> 原则是宁可说「没测到」，也不给一个现场能被翻数据推翻的答案。
> 所有数字的来源见 `docs/benchmark-report.md`。

## 一、关于竞品

**Q：这和 ClangBuildAnalyzer 有什么区别？它不已经给出每个头文件多少毫秒了吗？**

对，而且它给的比我们细：`-ftime-trace` 是真实编译器内省，我们只用自己的行数归因。
我们做过同任务对照：同一批 25 个编译单元、同一个 clang、同一条候选筛选规则，
把两边口径都还原成「自身成本 × 次数」后，Top-10 重合 **7/10**、Spearman ρ ≈ **0.68**。
换一个工程（doctest）是 **5/10**、ρ ≈ 0.57。

所以正确答案是：**在「找出最贵的头」这件事上我们不占优，只有中度一致性。**
我们的差异在它不做的两件事——把候选真的删掉编译一遍并复测，以及把结论固化成能拦回归的基线。

**Q：那它比我们好在哪？**

好在它能回答「现在花多少」，我们能回答「删了之后到底省不省」。但要注意措辞：
我们能**验证**，不承诺**找到**。理由见下面第二组问题。

**Q：为什么不做 IWYU / Build Insights 的对照？**

IWYU 需要按 LLVM 版本源码构建，本轮没做，记为未测；微软 Build Insights 在本机
因 `vcvars` 依赖被安全策略拦截的 `reg.exe` 无法运行，改用 CI 的 Windows runner 补
（见 `.github/workflows/msvc-evidence.yml`）。**没跑的一律不写成结论。**

## 二、关于「你们到底能不能优化」

**Q：你的工具能帮我把构建时间降下来吗？**

不能替你做保证。我们在一份真实工程上测过：工具推荐的前 10 条候选里，
**0 条**通过「编译成功且省时超过噪声」；随机抽 10 条 include 试删也是 0 条。
所以我们**撤回了「自动找到优化」这个说法**。

**Q：那是不是工具没用？**

不是。同一个管线在一个明确留了可删 include 的构造样本上测出 **1/6** 有效，
并且通过复测。所以 0 命中的原因是**那个工程的候选池里没有可复现的收益**，
不是测量失灵。这两件事必须分开说，否则会把「工程没得优化」误报成「工具坏了」。

**Q：所以它的价值是什么？**

把「看起来能省」变成「确认能省 / 确认不能省」，并把这个结论固化成基线。
具体是三件事：
1. 候选删掉后能不能编译（编译器说话，不是启发式）；
2. 真的省时吗（每侧 N 次取最小，判 improved 后还要复测一遍）；
3. 这个结论能不能拦住下一次回归（CI 门禁）。

**Q：为什么「已验证」要复测？**

因为我们自己测出来单遍不可靠：同一批候选连测三次，读数在 1.04%–2.10% 之间摆动，
`improved` 出现 1/3 次；第一轮判为 improved 的候选复测 **0/4** 复现。
现在 `verify --confirm` 默认 2，两遍都过才保留结论，代价是判定成本约翻倍（只对 improved 生效）。

## 三、关于门禁

**Q：门禁能挡住构建变慢吗？**

能挡住**一部分**。注入一次已知回归（新增一个 22,903 行的头）后 3/3 检出；
树不变时 3/3 通过、零误报；构建损坏导致编译单元减少时 3/3 拦截。单次门禁中位 **3.38 s**。

**Q：那漏报呢？**

有，且我们写进文档了：**行数不变但编译变慢的回归测不出来**，例如宏展开变复杂、
模板实例化变重。门禁挡的是「头文件覆盖面膨胀」，不是「构建变慢」的全部。

**Q：构建坏掉的时候门禁会怎样？**

这是我们实测中发现并修掉的一个真缺陷：旧逻辑只比较总成本，一个编译单元失败后
总量「下降」，门禁反而报 −67.7% 并**通过**。现在只要可用单元数少于基线就直接失败，
并提示「若有意删除请更新基线」。

## 四、关于数据可信度

**Q：你的数字跑一次就能复现吗？**

结构指标（归因行数、Top-10）三次完全一致。时间指标不是：单次测量 p90 抖动 12.9%，
min-of-3 后 p90 降到 1.89%，A/A 两次最大 delta 分别是 1.07% 与 **2.30%**。
所以我们不用单次测量下结论，也不把 2% 当绝对线——它是「典型噪声」的量级。

**Q：为什么报告里写了那么多不利数据？**

因为它们是这道题的答案。这个赛道的直接竞品（ClangBuildAnalyzer、Build Insights）
已经把「发现成本」做得很强，我们的诚实位置是「验证 + 治理」，而验证的价值恰恰取决于
敢不敢公开自己的失败率。

## 五、关于工程

**Q：开销多大？**

同任务下扫描墙钟是纯编译时间的 **1.15×**（GCC）/ **1.20×**（Clang），
分析本身独占 5.4–5.6 s，峰值内存 9.2 MB（主进程，不含编译器子进程）。

**Q：依赖什么？**

Python 标准库，零第三方依赖。实验脚本另外用到 `psutil` 采内存，那是实验工具，不是产品依赖。

**Q：支持 MSVC 吗？**

支持，且已有真实运行证据。本地 `vcvars64` 依赖被安全策略拦截的 `reg.exe`，
所以把验证放进 CI 的 windows-latest：`scan --compiler cl` 得到 **TU=2、失败 0、
归因行数 196,157**，随后 `gate` 无回归通过（run #5/#6 success，产物可下载）。

要一起说的是口径：同一个 demo 工程 GCC 归因 228,987 行、MSVC 196,157 行，差 14%——
因为两边包含的系统头是两套。**归因行数只能在同一编译器内纵向比较，跨编译器不可相减。**

**Q：下一步做什么？**

**2026-10-18 已完成换血**：候选生成扩到头文件级（`attrib/sites.py`，带可行性
闸门与收益放大），测量改成交替协议（聚合 A/A 从 2.005% 降到 0.644%）。G2 由
0/10 变为 doctest 上 1/5 可采纳、注入-召回 2/2，json 上 0/5。

**2026-10-18 两项都已做完，结论要连着读**：

- ② 第三个工程（zlib，C 语言，15 TU）复测：**0/5**，闸门开 0 条。加上 json 的
  0/5，三个工程里只有 doctest 是 1/5——**1/5 是少数情况，不是工具的能力**。
- ③ 排序换实测成本（`-ftime-trace`）：doctest 上 Top-1 从「删了编译不过的
  `algorithm`」变成「唯一可采纳的 `unordered_set`」。但它改善的是**排序**，
  不是**命中率**——候选集没变，1/5 还是 1/5。

下一步最该修的是：G2-4 只在 doctest 一个工程上测过，且 zlib 说明多数工程上
闸门会交白卷——**怎么在交白卷时给出有用的输出**（例如「这里没有可删的，成本
集中在哪几个头上」）比继续提高排名精度更值钱。
