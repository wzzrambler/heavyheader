# 基准报告 · 阶段 0：噪声底与确定性

> 日期：2026-10-18。本报告只报告**已测到**的东西；没测到的明确写「阻塞」。
> 复现：`python experiments/aa_noise.py --runs 3 --tus 25`
> 原始数据：`experiments/results/aa-20261018.{md,json}`

## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 结构指标是否确定？ | **是**。归因行数 4,233,937，三次运行完全一致；Top-10 列表也一致 |
| 计时噪声底多大？ | 单 TU 墙钟极差中位 **1.58%**；整轮扫描 0.89%；编译合计 1.50% |
| 扫描开销多少？ | 扫描 41.64 s vs 编译合计 35.47 s，**1.17×** |
| G1（公平对照）是否通过？ | **部分通过**。已与 ClangBuildAnalyzer 同编译器、同候选规则对照（§8）；Build Insights 与 IWYU 仍无法运行 |
| 与 CBA 的热点排序一致性？ | 同构口径下 Top-10 重合 **7/10**、Spearman ρ **0.69**；但 CBA 自己的顺序在两次运行间会变（§8.3） |

一句话：**同台已经做到，结论是「排序部分一致、口径差异可解释」，不是「我们更准」。**

## 1. 方法

- 工程：`experiments/_work/json`（nlohmann/json），编译数据库 63 条，取前 25 个 TU。
- 命令：`heavyheader scan --compile-commands … --max-tus 25 --jobs 1 --format json`。
- 同一输入、不改任何文件，重复 3 次；`--jobs 1` 降低并行调度噪声。
- 记录：归因行数、Top-10 项目头、整轮扫描墙钟、TU 墙钟合计、逐 TU 墙钟。

## 2. 结果

| 指标 | 数值 |
|---|---:|
| 编译单元 | 25（0 失败） |
| 归因行数 | 4,233,937 × 3，完全一致 |
| 扫描墙钟中位数 | 41.64 s |
| 扫描墙钟极差 | 0.89% |
| TU 墙钟合计中位数 | 35.47 s |
| TU 墙钟合计极差 | 1.50% |
| 单 TU 墙钟极差（中位） | **3.68%** |
| 单 TU 墙钟极差（p90） | **12.9%** |
| 单 TU 墙钟极差（最大） | 24.8% |
| 扫描 / 编译 | 1.17× |

**判读（两次会话差异显著）**：同一脚本先后跑过两次，单 TU 极差中位数
1.58% → 3.68%，p90 12.9%。**噪声底不是常数，随机器负载变化**，所以
「跑一次 A/A 就定阈值」是错的，必须每次会话先校准。

`verify` 不是单次测量：它对每侧编译 3 次取**最小值**。补测 min-of-3 的 A/A
（`experiments/noise_min3.py`，10 个 TU，两轮 min-of-3）：

| min-of-3 噪声 | 数值 |
|---|---:|
| 中位 | 0.72% |
| p90 | **1.89%** |
| 最大 | 2.63% |

结论：`TIME_NOISE_FLOOR = 2%` **高于 p90、略低于最大值**，在当前实现下成立，
但处于边界——极少数运行的噪声可达 2.63%。因此：阈值保留 2%，不调；
对接近阈值的结果，`verify --runs` 应加到 5 以上再判定。

## 3. 本轮抓到的缺陷：Top-10 曾经不稳定（已修）

第一次 A/A 跑出来：归因行数三次完全一致，但 **Top-10 列表三次不同**。

- 根因：`header_stats` 的插入顺序来自 `set` 迭代，而 `Path` 的哈希受 Python
  哈希随机化影响；排序键只有 `(归因行数, 覆盖 TU 数)`，并列时顺序由迭代顺序决定。
- 影响：任何「与竞品 Top-10 一致性」的对比都会把随机差异算成算法差异；
  基线 diff 也会出现假变化。
- 修复：排序键加路径作为最终 tie-breaker；`header_stats` 按路径排序后迭代；
  JSON 导出按路径排序。附回归测试。
- 复验：三次运行 Top-10 完全一致。

这类缺陷不会崩溃、数字也「看着合理」，只有 A/A 对照能抓到——这正是先做噪声底的价值。

## 3.5 本轮同时修掉的口径缺陷：verify 用的是 CPU 时间

`verify._measure()` 原先累加 `tu.total_wall_seconds()`，即 `-ftime-report` 的
**CPU 时间**；而 `scan.baseline_seconds` 已改为墙钟。两者量纲不同，报告里的
「节省 30 ms」与用户实际等待对不上（MinGW 实测 CPU 0.02s vs 墙钟 0.60s）。
已统一到 `models.tu_compile_seconds()`：优先驱动实测墙钟，缺失时退回 TOTAL。
保留「多次取最小值」的降噪策略不变。

## 4. 另一个口径问题：仓库内的第三方头

Top-1 是 `doctest.h`（`tests/thirdparty/` 下的测试框架，vendored 进仓库）。
当前分类规则是「路径在 root 下即视为项目头」，因此它被当成可治理对象。

这对 G1 不公平：竞品可能把它归为第三方。**在对照前必须先统一分类口径**，
否则「谁的 Top-1 是什么」根本不可比。已记为待决项（见 §6）。

## 8. G1 同任务对照：ClangBuildAnalyzer（2026-10-18）

### 8.1 环境与协议

- 工具链：clang 23.1.3（系统安装）、cmake 4.4.4（pip 装入隔离环境）、ninja（pip）；
  ClangBuildAnalyzer **1.6.0 从源码构建**（clang + ninja）。
- 同一批 **25 个 TU**，同一份 `compile_commands.json`。
- **同一个编译器与同一组参数**：两边都是 `clang++`，都带
  `--target=x86_64-w64-windows-gnu --gcc-toolchain=C:/mingw64`
  （clang 在 Windows 默认指向 MSVC 头，而本机 MSVC SDK 不可用）。
- **同一条候选筛选规则**：路径是否位于项目根下。系统头两边都不计入。
  不依赖各自的 `kind` 分类，避免分类口径差异污染对照。
- 两侧编译失败均为 **0 / 25**。

### 8.2 上一轮 1/10 是怎么来的：三个口径错误

上一轮报告过「重合 1/10」。那个数字不可用，原因已逐一定位：

1. **候选集合不同**：CBA 的榜单含系统头（`algorithm`、`sstream`、`set`…），我们只列项目头。
2. **CBA 默认配置只列「直接被 TU 包含」的头**（`onlyRootHeaders=true`，源码
   `src/Analysis.cpp` 的 `Config`），传递包含的头被整体排除；且 `header=10` 只输出
   10 行，去掉系统头后只剩 4 行——拿 4 项比 10 项。
3. **编译器不同**：CBA 侧 clang、HeavyHeader 侧 g++（当时 clang 扫描因
   `--flag` 在 `compile_commands` 模式下被丢弃而全部失败，见 §8.5）。

改掉这三点后，同一份数据给出的是下面这组数字。

### 8.3 主结果：还原成「自身耗时」后的同构比较

必须先说清一个口径事实：CBA 输出的每头文件时间是 `Source` 事件累加，而 trace 里的
`Source` 区间是**嵌套**的（u0 里 `json.hpp` 的 382 ms 区间完整包住
`adl_serializer.hpp` 的 113 ms 区间；25 个 TU 中共 673 个区间互相嵌套）。所以
CBA 的发布口径是「含子头」的耗时，而 HeavyHeader 的归因行数是「自身行数 × 包含次数」。
两者不同量，直接比会系统性低估一致性。

把原始 trace 按「区间长度 − 直接子区间」还原成**自身耗时**后（推导见
`experiments/cba_compare.py::trace_self_times`，可复核）：

| 指标 | 结果 |
|---|---|
| Top-10 集合重合 | **7 / 10** |
| 共同项顺序一致性（Kendall τ） | 0.33 |
| 全部 35 个共同项目头的秩相关（Spearman ρ） | **0.68** |

独立重复三次（同一协议），结果为 7/10、ρ = 0.69 / 0.68 / 0.68——**这一组可复现**。

作为参照，按 CBA 发布口径（含子头）比较时：重合 5/10、τ 0.20、ρ 0.42。
差异主要来自口径，不来自工具判断。

**这条结果支持什么、不支持什么**：
- 支持：在同构口径下，行数归因与真实解析耗时**中度偏强相关**，「结构排序」不是一个
  无意义的代理指标。
- 不支持：它**不能**说明我们比 CBA 准。7/10 意味着仍有 3 个不同的头文件进入各自前十，
  且 ρ ≈ 0.68 说明排序分歧不是个别现象。

### 8.4 排序分歧的原因：每千行解析成本差 60×

同为「自身成本」，差别只能来自头文件内部构成。25 个 TU 的合计：

| 头文件 | 自身耗时 | 归因行数 | 每千行耗时 |
|---|---:|---:|---:|
| `hedley.hpp` | 14.8 ms | 51,125 | **0.3 ms** |
| `doctest.h` | 217.4 ms | 177,650 | 1.2 ms |
| `binary_writer.hpp` | 101.9 ms | 45,950 | 2.2 ms |
| `binary_reader.hpp` | 278.8 ms | 75,225 | 3.7 ms |
| `json.hpp` | 1411.6 ms | 131,450 | 10.7 ms |
| `exceptions.hpp` | 112.2 ms | 6,425 | **17.5 ms** |

在归因行数 ≥ 5,000 的 20 个头上，最便宜的 `hedley.hpp`（纯宏与声明）与最贵的
`exceptions.hpp`（模板实例化密集）相差 **60×**。

> 门槛是必要的：不设门槛时极值来自一个 120 行的头（177.9 ms/千行），
> 那是除法的产物，不是真实差异。**归一化指标必须声明样本量下限。**

结论很直接：**行数只能用来筛候选，不能用来下成本结论**。成本结论只能来自实测——
这正是 `verify` 存在的理由，也是本轮数据对定位的支持。

### 8.5 同时修掉的真缺陷：`--flag` 在 compile_commands 模式下被丢弃

上一轮 clang 侧 25 个 TU 全失败，根因不是 clang 配置，而是我们自己的 bug：
`scan_project()` 只在任务「没有自带 flags」时才注入 CLI 参数，于是
`--flag=--target=…` 被 argparse 接受、被 `--reproduce` 打印，然后在装配阶段静默丢弃，
clang 于是去链不可用的 MSVC 头。已修为：任务自带 flags 时**追加**而非丢弃 CLI 参数，
并加回归测试。

### 8.6 CBA 自身的榜单稳定性：集合稳、顺序不稳

比较两个工具的排序前，必须先知道对方排序本身可不可复现
（`experiments/cba_stability.py`，同输入独立跑两遍）：

| 口径 | 集合稳定 | 顺序稳定 |
|---|---|---|
| CBA 发布口径（含子头） | 是 | **否**（`input_adapters` / `serializer` / `doctest_compatibility` 位置互换） |
| CBA 自身耗时口径 | 是 | 是（仅两遍观测） |
| HeavyHeader（A/A 三轮，§2） | 是 | 是 |

单头文件耗时最大抖动 **9.0%**（`json_sax.hpp`）。这解释了一个具体现象：同一份数据
按发布口径算出的 τ 在两次运行间从 0.20 跳到 0.40——**不是我们的结论在变，是对方
接近并列的位置在变**。

因此报告里对顺序类指标的口径统一为：**只在同构口径（自身耗时）上报告 τ 与 ρ**，
发布口径只作参照；且 τ 接近 0 时不得解读为「排序无关」，因为并列抖动本身就足以把它压低。
