# 五分钟演示脚本：一条候选走完主线

> 这份脚本对应评审反馈里最重要的一条：**不要再增加页数，把现有证据收束成一场演示**。
> 目标只有一个——让评委亲眼看到「删掉这行 include 会怎样」是一次**受控实验**，
> 而不是一句静态推断。全片围绕**一个候选**（`lonely.h`）走完四步：
> 成本热点 → 反事实验证 → 闸门拦下/确认 → 进 CI 门禁。

## 一句话主张

> 团队知道「大概是头文件太多」，不知道**哪一条、值多少、删了会不会出事**。
> HeavyHeader 把「该不该动手」变成一次扫描，把「动了有没有用」变成一次重建。

## 演示前准备（提前 5 分钟，不要在现场等）

```bash
cd heavyheader
pip install -e .                 # 或 pip install heavyheader（PyPI 已发布 v0.1.0）
g++ --version                    # 现场用 MinGW-w64 的 g++；换 clang++ 也行，加 --compiler 指定
```

现场只需要**一个终端窗口**和**仓库里的 `benchmarks/cases/demo`**——这是一个为演示造的
小工程（2 个编译单元、7 个头文件），**不是真实项目**。真实项目的数字一律引用
`experiments/results/` 下的归档结果（见文末「评委想自己核」），演示中明确说明这一点。

> ⚠️ 纪律：`lonely.h` 的 −15.1% 是**演示语料**上的数字，不能当成真实工程的收益去讲。
> 真实工程的口径在作品介绍文档 4.6–4.8（zstd 单条 −46.6%、池内采纳率 25% 及其分母）。

## 第一步：成本热点（0:00–0:45）

```bash
heavyheader scan benchmarks/cases/demo --compiler g++ --std c++17 --format md
```

屏幕上指这三行，不要念完整报告：

| 指哪 | 说什么 |
|---|---|
| `2 TU · 368 条依赖边 · 166,159 行头文件解析量` | 两个文件，被迫解析 16 万行头文件 |
| `include\lonely.h`：独占闭包 **36**、预计省 **22,316 行（15.9%）** | 删掉它，只有它会停止被解析——这就是「独占闭包」 |
| 同一行的「使用状态」列写着 **正在使用**，判据是「副作用：template<typename _Bi_iter…」 | **静态判据说它在用** |

> 口播：「注意最后一格。这个头文件声明了一个从没被调用的函数，却拖着一整套
> `<regex>`。文本判据看到 `<regex>` 里的模板就判『在用』——它分不清
> 『被使用』和『顺带被解析』。所以我们需要第二步：别猜，删了试试。」

## 第二步：反事实验证（0:45–2:00）

```bash
heavyheader verify benchmarks/cases/demo --compiler g++ --std c++17 \
    --ungated-sites --top 5 --runs 3 --confirm 2
```

`--ungated-sites` 的意思是：**把静态判据拦下的候选也送去测**。屏幕上会出现五种结局里的两种：

- 4 条 `compile-error`——逐个报出 `error: 'Core' was not declared in this scope`；
- 1 条 `improved`——**基线 720 ms → 移除后 612 ms（−15.1%）**，
  证据档写着「**已验证**：汇编指纹一致、实测省时过噪声线、复测仍成立」。

> 口播：「这一步是工具肯认错的地方。它不是说『建议你删』，它是真的删掉、真的编译、
> 两侧各编三遍取最小、再复测一遍。编不过就写编不过，汇编变了就写变了。
> 判据说『在用』的这条，编译器说是可删的——**判据说不清的地方，编译器说得清**。」

小结行还印着一句可以直接念的话：

> 「其中 1 条被文本判据判为『在用 / 无法判定』，是闸门证据把它们抬到上两档的。」

## 第三步：闸门拦下「看起来无害的破坏性改动」（2:00–3:00）

这一步现场造一个**最小复现**（10 秒，三个文件），对应真实工程里的 spdlog 案例
（−77.8% 的「提升」其实是把函数定义删掉了，汇编从 10,329 行塌缩到 40 行）：

```bash
mkdir -p /tmp/linktrap && cd /tmp/linktrap
printf '#pragma once\nint helper();\n'                        > decl.h
printf '#pragma once\n#include "decl.h"\nint helper(){return 42;}\n' > defs.h
printf '#include "decl.h"\n#include "defs.h"\nint main(){return helper()-42;}\n' > main.cpp
heavyheader verify /tmp/linktrap --compiler g++ --std c++17 --check-codegen
```

屏幕上会出现（实测输出）：

```
## defs.h ← main.cpp
   状态：codegen-changed — 移除后编译通过，但生成的代码与原来不同
   （差异原因需人工判断：条件编译、重载解析选中的定义，或链接期才暴露的缺失定义都有可能）
代码等价闸门：跑了 1 条，拦下 1 条（汇编变了，已判 codegen-changed）。
```

> 口播：「`-fsyntax-only` 对它完全沉默——它编得过。但 `helper()` 的**定义**本来是由
> 这个头提供的，删掉之后目标文件里就没有它了，链接期才炸。
> 第三条真值（汇编指纹）把它拦下来了。注意这句提示：工具只说『不一样』，
> **不猜为什么**——成因要人看。」

（时间不够就跳过现场造文件，直接放 `experiments/results/corpus-timing-spdlog-20261019.md`
里的 spdlog 案例，一句话带过：「真实工程上同一条闸门拦下过 −77.8% 的假收益」。）

## 第四步：进 CI 门禁（3:00–4:00）

```bash
cp -r benchmarks/cases/demo /tmp/gatedemo
heavyheader scan /tmp/gatedemo --compiler g++ --std c++17 --save /tmp/baseline.json
echo '#include <regex>' >> /tmp/gatedemo/include/core.h     # 模拟一次「顺手加个头」
heavyheader gate /tmp/gatedemo --compiler g++ --std c++17 --baseline /tmp/baseline.json
echo "exit=$?"
```

屏幕上会出现（实测输出）：

```
门禁失败：
  - header cost regressed +23.9% (206106 -> 255280 attributed lines), budget is +5.0%
  -   worst offender: .../bits/regex.h 3140 -> 6280 lines (+100.0%)
exit=1
```

> 口播：「这一行是这件事能不能长期成立的关键。优化一次不算本事，不让它退回去才算。
> 成本是有基线的、有门禁的——`--max-regression` 一接就能挂进 CI。
> 真实工程上这条门禁注入回归 3/3 检出、无回归 3/3 放行、构建损坏 3/3 拦截。」

## 第五步：收束成三句话（4:00–5:00）

不要总结功能，总结**方法论**。屏幕上停在这一页（对应作品介绍文档「评审速读」）：

1. 问题不是找出昂贵的头文件，而是**证明删掉某一条 include 是否真的有净收益**；
2. 只编译通过不够，必须防止性能数字来自**被破坏的程序**；
3. 这不是一次性分析工具，而是一条**可复现、可审查、可接入 CI 的治理链路**。

然后主动补三条边界（评委追问前先说，可信度更高）：

- 「25% 是**池内采纳率**（5/20），不是端到端准确率也不是召回率；同池换协议是 40%，
  两遍成员只重合 3 条——它证明的是筛选方法有价值，还不是稳定预测器。」
- 「两条上游 PR（doctest#1212、madler/zlib#1344）截至 2026-10-21 都是 open、
  未被合并；我们只写『已提交』。」
- 「演示语料是仓库里造的，真实项目数字在 `experiments/results/`，随时可核。」

## 常见提问的答法

| 提问 | 答 |
|---|---|
| 这和 IWYU / clang-include-cleaner 什么关系？ | 互补。它判**正确性**（AST 级，该不该包含），我们判**成本**（这条 include 让你多等几秒、删了会不会出事）。同一工程同任务实测：它给 0 条删除建议、101 条补充建议；我们 222 个候选逐条真编译，得到 1 条 −43.5%。它的 101 条补充建议我们一条也给不出。 |
| 为什么不直接上 PCH / ccache？ | 它们回答「怎么加速」，我们回答「**加速哪里、以及这次加速有没有把程序改坏**」。 |
| 25% 是不是太低？ | 分母要说清：送测池 20 条 = 三真值已证实 ∩ 预估过噪声线。端到端是 5/222 = 2.3%。25% 证明的是「筛出来的候选约四分之一真能省」，不是准确率。 |
| 编过不就行了，为什么要比汇编？ | 因为编过不等于程序没变。spdlog 上 −77.8% 的「优化」汇编从 10,329 行塌到 40 行；brotli 31 个站点里 3 条编得过但汇编变了。只做 `-c` 不链接的探针对「少一个函数定义」是静默的。 |
| 你们比 ClangBuildAnalyzer 准吗？ | 不比准。同一批 25 TU 同口径对比 Top-10 重合 7/10、ρ ≈ 0.68——**中度一致**。这正是我们坚持「行数只用来筛候选、成本结论只能来自实测」的原因。 |
| 上游合并了吗？ | 没有。两条 PR 都是 open，合并与否由维护者决定，结果会更新进仓库状态表。 |
| 只有一个演示工程？ | 演示工程是仓库里造的，为了让评委看见过程。真实工程数据在 `experiments/results/`：zstd 39 TU / 350 万行、brotli 32 TU、Lua 34 TU、doctest / zlib / spdlog / nlohmann-json。 |

## 评委想自己核

作品介绍文档 **0.1「每个大数字从哪里复现」**是一张对照表：左边是文档里引用的每个大数字，
右边是原始记录文件、测量环境与复现命令。所有原始记录在 `experiments/results/`，
脚本在 `experiments/`，均可用 `python experiments/<脚本>.py` 重跑。

换机器、换编译器，数字会变、方向不变——所以每一行都写了测量环境。

## 现场备案

| 情况 | 备案 |
|---|---|
| 现场没有 g++ | 用 `--compiler` 指定 clang++；两者都实测过（clang++ 在 Windows 上会吃到 MSVC 头文件，判据的「副作用」提示文本不同，结论不变） |
| 编译太慢等结果 | `--top 2` 只测前两条；或者直接切到预生成的 `experiments/results/verified-layer-lua-20261020.md` 讲同一套流程 |
| 被问到没准备的数据 | 作品介绍文档 4.8 有三指标表与「不能用来回答什么」一列，照着念即可 |
