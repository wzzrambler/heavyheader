# 场景落地：开源 C/C++ 工程的头文件成本治理

> 本文回答评审第二项（场景落地，30%）的四个问题：**需求是否真实、方案是否适配场景、
> 是否可部署/可运行/可测试、验证是否来自真实环境。** 全部数字来自本仓库
> `experiments/` 的实测记录，可直接复现；估算与实测分列，不合并。
> 日期：2026-10-19。

## 1. 场景定义

**谁在这个场景里**：任何一个 C/C++ 工程——尤其是持续集成里的开源库与商业代码库。
**他的痛处**（真实且普遍）：

- 一次全量构建几十分钟到几小时，CI 机时与工程师等待都花在里面；
- 慢的最大单一来源往往不是算法，而是**头文件失控**——一个被几万个编译单元传递
  包含的重型头，让整个项目反复为它付费；
- 他手上的工具只能回答「谁贵」（排行榜）或「缺什么」（lint），到了「那我删一个试试、
  值不值」就没有工具了——这一步今天仍靠人的经验与手动试验。

HeavyHeader 适配这个场景的方式不是再加一个排行榜，而是接管**从发现到守住**的全链路，
并把每一步的证据留给用户复核。

## 2. 全链路：四步，每步都有实测

```
① scan    成本归因：归因行数 / Blowup Factor / 独占闭包 / 模板实例化成本
            ↓ 给出候选与「为什么删不掉」的白卷诊断
② verify   反事实实验：注释掉候选行、真实重编、交替 A/B 实测
            ↓ Δ时间 / Δ内存 / Δ体积，越过会话内噪声线才算数
③ 决策    三态结论：建议删除 / 保留 / 需人工判断，每条带三维度证据与复现命令
            ↓
④ 守住    gate（CI 门禁，指名回归头文件）+ pr-comment（PR 评论）+ history（趋势看板）
```

### ① 发现：成本在哪，删不删得动

- nlohmann/json（25 TU）：归因 4,233,937 行，三次运行**完全一致**，Top-10 稳定；
- 白卷诊断（0 条可删时）：json 369 条、zlib 58 条收益非零的 include 行被逐条判过，
  每条附标识符证据或「位于系统/第三方头内部」——0 条候选时工具交的是一份
  可核对的原因清单，不是一张空表（`experiments/results/g2-diagnosis-*`）。

### ② 验证：反事实实验（本场景的核心动作）

- 注入-召回（往真实工程注入一条确实多余的 `#include <regex>`）：头文件级
  候选排 **1/17**、TU 级排 **25/61**，两条均被两遍独立实测证实（−6.82% / −6.14%，
  −5.77% / −6.65%）；
- 测量协议：每侧 min-of-3、B/P/B/P 交替、TU 级噪声线 2% / 聚合 1%、improved
  强制复测 2 遍——协议的每个部件都对应一个实测到的失败模式
  （[`docs/innovation.md`](innovation.md) §3.2）。

### ③ 决策：222 个候选，没有一条停留在「疑似」

nlohmann/json 上 222 个候选**全部真实编译**（`decision_check.py`）：

| 结论 | 数量 | 含义 |
|---|---:|---|
| 建议删除 | **1** | 编译通过且耗时下降超过噪声线 |
| 保留 | 187 | 编译器已否决或定位不到注释位置 |
| 需人工判断 | 34 | 编译可行但收益在噪声内，全部附倾向与理由 |

唯一「建议删除」的三个维度全部实测：时间 −43.5%、内存 −43.9%、体积 −0.05%
（阴性维度也列出）。**「能给明确结论」不等于「结论都对」**——187/222 编译不过是
事实，报告因此把「保留」也当作一等公民展示。

### ④ 守住：门禁真的拦得住

注入回归 3/3 检出、无回归 3/3 通过（误报 0）、构建损坏 3/3 拦截——构造样本与
真实工程（nlohmann/json 25 TU，4,491,172 行）双重复验；单次门禁中位 3.38 s
（构造样本）/ 30.3 s（真实工程）。修过的严重缺陷记录在案：注入导致 TU 从 2 掉到 1
时总成本算出 −67.7%、门禁曾**通过**（越坏越绿）——已改为可用单元少于基线直接失败。

## 3. 三个真实工程的数据卡

| 工程 | 语言 | TU | 场景内结论 | 关键数字 |
|---|---|---:|---|---|
| nlohmann/json v3.11.3 | C++ | 63 | 完整构建 A/B（PCH 治理） | 墙上 **−7.1%**、编译 CPU **−11.4%**、63 套件 **4,264,414 条断言逐个一致** |
| nlohmann/json | C++ | 25 | 逐 include 决策层 | 222 候选：**1 删 / 187 留 / 34 人工**；1 条 −43.5% |
| doctest | C++ | 24 | 优化闭环 | 删 `prelude.h` 的 `<unordered_set>`：24 单元全过、聚合 **−3.01%**、复测通过（**1/16**） |
| zlib | C | 15 | 优化闭环（关闸门召回） | 删 `zutil.h` 的 `<stdlib.h>`：9 单元全过、3314 → 3244 ms（**−2.125%**）、复测通过（**1/16**） |
| fmt / spdlog / cpp-httplib | C++ | — | 基线扫描 | `benchmarks/run_all.py` 一键复现 |

必须一起说的诚实事实：三个工程的天然候选采纳率是 **1/16、1/16、0/16**——
「自动帮你找到优化」不成立；「可验证地找到并证实一条、且把它变成上游改动」成立
（§4）。PCH 的完整构建收益（−11.4% CPU）回答的是另一个问题：**该往哪使劲**，
两个结论都来自实测，不互相顶替。

## 4. 最后一公里：上游 PR 战役

实验证据落在我们克隆的副本上是不够的——这个场景的终点是**真实工程真的接受这个
改动**。`contrib/upstream/` 记录了两条已实测的优化如何变成上游 PR：

- doctest：删 `doctest/prelude.h` 里的 `#include <unordered_set>`（−3.01%，24 单元
  全通过，复测通过）；
- zlib：删 `zutil.h` 里的 `#include <stdlib.h>`（−2.125%，9 单元全通过，复测通过；
  这条是关掉可行性闸门才召回的，PR 文案里如实注明）。

每条 PR 的数据、复现命令与「验证覆盖到哪里、没覆盖到哪里」（如下游使用者、
平台条件编译分支）都写进 PR 正文。战役状态与提交方式见
[`contrib/upstream/README.md`](../contrib/upstream/README.md)。

## 5. 可部署 / 可运行 / 可测试

| 评审关切 | 事实 | 证据 |
|---|---|---|
| 可部署 | 零第三方运行时依赖，Python 3.10+ 标准库；源码安装一条命令；MSVC / GCC / Clang 三套驱动 | `pyproject.toml` `dependencies = []` |
| 可运行 | 4 个真实开源工程基准一键复现；三编译器横评；MSVC 真实运行证据在 CI 产物里 | `benchmarks/run_all.py`；`.github/workflows/msvc-evidence.yml` |
| 可测试 | **499 个测试全绿**；CI 覆盖三大操作系统 × 四个 Python 版本 | `.github/workflows/ci.yml` |
| 开销可接受 | 扫描开销 1.15×（g++）/ 1.20×（clang++），峰值 9.2 MB，三次完全确定 | `docs/benchmark-report.md` §11 |
| 验证来自真实环境 | 全部实验工具链：真实开源工程快照（SHA-256 固定）、真实编译器、真实 CI；无玩具数据 | `experiments/fetch.py` 校验 |

竞品同任务对照也在这个场景里完成：clang-include-cleaner 同工程同任务（64 单元）
——它 0 条删除建议、101 条补充建议、恰好在唯一有效单元上分析失败；我们 222 条
候选逐条实测、1 条 −43.5%。结论是互补而非胜出，报告原文见
`experiments/results/competitor-20261018.md`。

## 6. 复现入口

```bash
python experiments/fetch.py            # 固定快照（SHA-256 校验，约 400 MB 语料）
python experiments/decision_check.py   # ③ 决策层：222 候选全部实测（约 6 分钟）
python experiments/run_experiment.py   # nlohmann/json 完整构建 A/B（约 9 分钟）
python experiments/control.py          # 与经验法则的对照 + 内建 A/A 空对照
python experiments/competitor.py       # clang-include-cleaner 同任务对照
benchmarks/run_all.py                  # 4 个真实工程基线扫描
```
