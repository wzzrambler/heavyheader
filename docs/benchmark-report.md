## 1. 方法

- 工程：`experiments/_work/json`（nlohmann/json），编译数据库 63 条，取前 25 个 TU。
- 命令：`heavyheader scan --compile-commands … --max-tus 25 --jobs 1 --format json`。
- 同一输入、不改任何文件，重复 3 次；`--jobs 1` 降低并行调度噪声。
- 记录：归因行数、Top-10 项目头、整轮扫描墙钟、TU 墙钟合计、逐 TU 墙钟。

## 2. 结果

| 指标 | 数值 |
|---|---:|
| 编译单元 | 25（0 失败） |
| 归因行数 | 4,233,937 × 3，完全一致 |
| 扫描墙钟中位数 | 41.64 s |
| 扫描墙钟极差 | 0.89% |
| TU 墙钟合计中位数 | 35.47 s |
| TU 墙钟合计极差 | 1.50% |
| 单 TU 墙钟极差（中位） | **3.68%** |
| 单 TU 墙钟极差（p90） | **12.9%** |
| 单 TU 墙钟极差（最大） | 24.8% |
| 扫描 / 编译 | 1.17× |

**判读（两次会话差异显著）**：同一脚本先后跑过两次，单 TU 极差中位数
1.58% → 3.68%，p90 12.9%。**噪声底不是常数，随机器负载变化**，所以
「跑一次 A/A 就定阈值」是错的，必须每次会话先校准。

`verify` 不是单次测量：它对每侧编译 3 次取**最小值**。补测 min-of-3 的 A/A
（`experiments/noise_min3.py`，10 个 TU，两轮 min-of-3）：

| min-of-3 噪声 | 数值 |
|---|---:|
| 中位 | 0.72% |
| p90 | **1.89%** |
| 最大 | 2.63% |

结论：`TIME_NOISE_FLOOR = 2%` **高于 p90、略低于最大值**，在当前实现下成立，
但处于边界——极少数运行的噪声可达 2.63%。因此：阈值保留 2%，不调；
对接近阈值的结果，`verify --runs` 应加到 5 以上再判定。

## 3. 本轮抓到的缺陷：Top-10 曾经不稳定（已修）

第一次 A/A 跑出来：归因行数三次完全一致，但 **Top-10 列表三次不同**。

- 根因：`header_stats` 的插入顺序来自 `set` 迭代，而 `Path` 的哈希受 Python
  哈希随机化影响；排序键只有 `(归因行数, 覆盖 TU 数)`，并列时顺序由迭代顺序决定。
- 影响：任何「与竞品 Top-10 一致性」的对比都会把随机差异算成算法差异；
  基线 diff 也会出现假变化。
- 修复：排序键加路径作为最终 tie-breaker；`header_stats` 按路径排序后迭代；
  JSON 导出按路径排序。附回归测试。
- 复验：三次运行 Top-10 完全一致。

这类缺陷不会崩溃、数字也「看着合理」，只有 A/A 对照能抓到——这正是先做噪声底的价值。

## 3.5 本轮同时修掉的口径缺陷：verify 用的是 CPU 时间

`verify._measure()` 原先累加 `tu.total_wall_seconds()`，即 `-ftime-report` 的
**CPU 时间**；而 `scan.baseline_seconds` 已改为墙钟。两者量纲不同，报告里的
「节省 30 ms」与用户实际等待对不上（MinGW 实测 CPU 0.02s vs 墙钟 0.60s）。
已统一到 `models.tu_compile_seconds()`：优先驱动实测墙钟，缺失时退回 TOTAL。
保留「多次取最小值」的降噪策略不变。

## 8. G1 同任务对照：ClangBuildAnalyzer（2026-10-18）

### 8.1 环境与协议

- 工具链：clang 23.1.3（系统安装）、cmake 4.4.4（pip 装入隔离环境）、ninja（pip）；
  ClangBuildAnalyzer **1.6.0 从源码构建**（clang + ninja）。
- 同一批 **25 个 TU**，同一份 `compile_commands.json`。
- **同一个编译器与同一组参数**：两边都是 `clang++`，都带
  `--target=x86_64-w64-windows-gnu --gcc-toolchain=C:/mingw64`
  （clang 在 Windows 默认指向 MSVC 头，而本机 MSVC SDK 不可用）。
- **同一条候选筛选规则**：路径是否位于项目根下。系统头两边都不计入。
  不依赖各自的 `kind` 分类，避免分类口径差异污染对照。
- 两侧编译失败均为 **0 / 25**。

### 8.2 上一轮 1/10 是怎么来的：三个口径错误

上一轮报告过「重合 1/10」。那个数字不可用，原因已逐一定位：

1. **候选集合不同**：CBA 的榜单含系统头（`algorithm`、`sstream`、`set`…），我们只列项目头。
2. **CBA 默认配置只列「直接被 TU 包含」的头**（`onlyRootHeaders=true`，源码
   `src/Analysis.cpp` 的 `Config`），传递包含的头被整体排除；且 `header=10` 只输出
   10 行，去掉系统头后只剩 4 行——拿 4 项比 10 项。
3. **编译器不同**：CBA 侧 clang、HeavyHeader 侧 g++（当时 clang 扫描因
   `--flag` 在 `compile_commands` 模式下被丢弃而全部失败，见 §8.5）。

改掉这三点后，同一份数据给出的是下面这组数字。

### 8.3 主结果：还原成「自身耗时」后的同构比较

必须先说清一个口径事实：CBA 输出的每头文件时间是 `Source` 事件累加，而 trace 里的
`Source` 区间是**嵌套**的（u0 里 `json.hpp` 的 382 ms 区间完整包住
`adl_serializer.hpp` 的 113 ms 区间；25 个 TU 中共 673 个区间互相嵌套）。所以
CBA 的发布口径是「含子头」的耗时，而 HeavyHeader 的归因行数是「自身行数 × 包含次数」。
两者不同量，直接比会系统性低估一致性。

把原始 trace 按「区间长度 − 直接子区间」还原成**自身耗时**后（推导见
`experiments/cba_compare.py::trace_self_times`，可复核）：

| 指标 | 结果 |
|---|---|
| Top-10 集合重合 | **7 / 10** |
| 共同项顺序一致性（Kendall τ） | 0.33 |
| 全部 35 个共同项目头的秩相关（Spearman ρ） | **0.68** |

独立重复三次（同一协议），结果为 7/10、ρ = 0.69 / 0.68 / 0.68——**这一组可复现**。

作为参照，按 CBA 发布口径（含子头）比较时：重合 5/10、τ 0.20、ρ 0.42。
差异主要来自口径，不来自工具判断。

**这条结果支持什么、不支持什么**：
- 支持：在同构口径下，行数归因与真实解析耗时**中度偏强相关**，「结构排序」不是一个
  无意义的代理指标。
- 不支持：它**不能**说明我们比 CBA 准。7/10 意味着仍有 3 个不同的头文件进入各自前十，
  且 ρ ≈ 0.68 说明排序分歧不是个别现象。

### 8.4 排序分歧的原因：每千行解析成本差 60×

同为「自身成本」，差别只能来自头文件内部构成。25 个 TU 的合计：

| 头文件 | 自身耗时 | 归因行数 | 每千行耗时 |
|---|---:|---:|---:|
| `hedley.hpp` | 14.8 ms | 51,125 | **0.3 ms** |
| `doctest.h` | 217.4 ms | 177,650 | 1.2 ms |
| `binary_writer.hpp` | 101.9 ms | 45,950 | 2.2 ms |
| `binary_reader.hpp` | 278.8 ms | 75,225 | 3.7 ms |
| `json.hpp` | 1411.6 ms | 131,450 | 10.7 ms |
| `exceptions.hpp` | 112.2 ms | 6,425 | **17.5 ms** |

在归因行数 ≥ 5,000 的 20 个头上，最便宜的 `hedley.hpp`（纯宏与声明）与最贵的
`exceptions.hpp`（模板实例化密集）相差 **60×**。

> 门槛是必要的：不设门槛时极值来自一个 120 行的头（177.9 ms/千行），
> 那是除法的产物，不是真实差异。**归一化指标必须声明样本量下限。**

结论很直接：**行数只能用来筛候选，不能用来下成本结论**。成本结论只能来自实测——
这正是 `verify` 存在的理由，也是本轮数据对定位的支持。

### 8.5 同时修掉的真缺陷：`--flag` 在 compile_commands 模式下被丢弃

上一轮 clang 侧 25 个 TU 全失败，根因不是 clang 配置，而是我们自己的 bug：
`scan_project()` 只在任务「没有自带 flags」时才注入 CLI 参数，于是
`--flag=--target=…` 被 argparse 接受、被 `--reproduce` 打印，然后在装配阶段静默丢弃，
clang 于是去链不可用的 MSVC 头。已修为：任务自带 flags 时**追加**而非丢弃 CLI 参数，
并加回归测试。

### 8.6 CBA 自身的榜单稳定性：集合稳、顺序不稳

比较两个工具的排序前，必须先知道对方排序本身可不可复现
（`experiments/cba_stability.py`，同输入独立跑两遍）：

| 口径 | 集合稳定 | 顺序稳定 |
|---|---|---|
| CBA 发布口径（含子头） | 是 | **否**（`input_adapters` / `serializer` / `doctest_compatibility` 位置互换） |
| CBA 自身耗时口径 | 是 | 是（仅两遍观测） |
| HeavyHeader（A/A 三轮，§2） | 是 | 是 |

单头文件耗时最大抖动 **9.0%**（`json_sax.hpp`）。这解释了一个具体现象：同一份数据
按发布口径算出的 τ 在两次运行间从 0.20 跳到 0.40——**不是我们的结论在变，是对方
接近并列的位置在变**。

因此报告里对顺序类指标的口径统一为：**只在同构口径（自身耗时）上报告 τ 与 ρ**，
发布口径只作参照；且 τ 接近 0 时不得解读为「排序无关」，因为并列抖动本身就足以把它压低。

### 8.8 第二个工程：doctest（24 个 TU）

同一协议换一个工程重跑，看 7/10 与 ρ≈0.68 是不是这个工程特有的：

| 工程 | TU | 同构口径重合 | τ | ρ | 发布口径重合 |
|---|---:|---:|---:|---:|---:|
| nlohmann/json | 25 | **7/10** | 0.33 | **0.68** | 5/10 |
| doctest | 24 | **5/10** | 0.20 | **0.57** | 6/10 |

两侧编译失败均为 0。结论要分两层：

- **两处都是「中度一致」**，没有出现「几乎完全一致」也没有出现「完全无关」，
  这说明行数归因作为候选排序指标是可用的；
- **但数值随工程变化明显**（7/10→5/10、ρ 0.68→0.57），所以任何单个工程上的
  重合率都不能当成普适结论，更不能用来支撑「比竞品准」。

doctest 这个样本还有一点值得记：它把实现拆成 `doctest/parts/private/**` 多个
小 .cpp，每个都 include 同一套头文件，正是「同一批头被大量 TU 重复解析」的形态，
和 json 的测试目标结构不同——这使它的对照更有独立价值。

## 9. G2：优化闭环（2026-10-18 重做后成立，有限）

### 9.1 旧判定为什么不充分

第一版协议（`experiments/g2_loop.py`）在 nlohmann/json 前 25 个 TU 上跑出
0/10，据此判 G2 不成立。那个 0 的来源后来被拆开了，拆开之后结论变了：

| 来源 | 证据 | 处置 |
|---|---|---|
| 候选空间太窄 | 83 条 TU 级候选里只有 3 条「疑似未使用」；把 include 图摊到所有文件后有 432 对 | 新增头文件级候选（`attrib/sites.py`） |
| 测量协议太钝 | 先测完基线再测补丁：聚合 A/A 差 **2.005%** | 改成交替测量：0.644% / 0.245% |
| 可行性判定被自己污染 | `#include <regex>` 这一行让包含者「用过 regex」 | 抹掉 include 行再取标识符 |

第三条最值得单独说：尖括号 include 里的文件名是个裸词，而它指向的头文件
往往声明同名的东西。于是用法判定命中的是自己造出来的匹配，结论恒为
「在用」——**注入-召回实验因此得 0/1，查下来不是工具找不到，是判定被污染了**。

### 9.2 换掉的两样东西

**（1）候选生成：从「TU 的 include」扩到「任一文件的 include」。**
一个 TU 只 include 两三个文件，几乎全是要用的；头文件不一样——它被几十个
TU 反复解析，里面一条多余的 include 的收益是 `独占行数 × 受影响 TU 数`。
生成器自带**可行性闸门**：拥有这一行的文件自己若不用它，才进入推荐列表
（闸门可关，用于消融对照）。工具链头不做站点（"去改 `windows.h`"不是建议）。

**（2）测量协议：聚合 + 交替。**
一次改动影响 N 个单元，判定必须用它们的耗时**之和**；而求和之后噪声并不会
互相抵消——实测三次聚合耗时 20299 / 20269 / 20675 ms，第三次整体高 2%，
这是**同一批测量期间的机器漂移**，不是各单元独立抖动。所以要把 B/P/B/P
排进同一时间窗：

| 协议 | 聚合 A/A 差异 | 出处 |
|---|---|---|
| 先测完基线、再测补丁 | **2.005%** | `experiments/results/g2-aggregate-aa-doctest-20261018.json` |
| 交替 min-of-3 | **0.644% / 0.245%** | `experiments/results/g2-interleaved-aa-doctest-20261018.json` |

因此聚合口径的阈值取 `AGGREGATE_NOISE_FLOOR = 1%`（在观测最大值上留余量），
TU 级仍用 `TIME_NOISE_FLOOR = 2%`。两者分母不同，混用会放松或收紧标准。

|---|---:|---:|---:|---:|
| feasible（闸门开，按放大收益取前 5） | 5 | 1 | **1** | **20%** |
| ungated（闸门关，按收益取前 5） | 5 | 0 | 0 | **0%** |

闸门开的那条命中是：`prelude.h` 里删掉 `#include <unordered_set>`，
24 个单元全部编译通过，聚合耗时 **20556 → 19937 ms（−3.01%）**，并通过复测。

注意门槛的口径：**无闸门臂 0/5 编译通过，闸门臂里那 1 条既能编过又真省时**。
闸门不是把命中率变成 100% 的魔法，它做的是把「候选里有多少条值得动编译器」
从 0/5 提到 1/5，并且这 1 条是真收益。剩下 4 条删了编译不过——它们是启发式的
假阳性，被 `verify` 挡住了，这正是两个阶段要分开的理由。

> **2026-10-18 补充**：上面这个「0/5 → 1/5」的解释已经不成立。全量三档探测
> （§9.8）显示闸门放行 16 条通过率 50%、完全不筛 66 条通过率 47%——闸门对
> 「能不能编」没有预测力，它只是把候选砍到 1/4。本段保留作为过程记录，
> 结论以 §9.8 为准。

### 9.3b 把 16 条全部测完：闸门的真实通过率是 8/16

上面那张表的「前 5 条」是排序后的截断。「只测了 5 条」是最容易被追问的一点，
所以这一轮把闸门放行的 **16 条全部**测完（`--arms feasible --top 16`，
`experiments/results/g2-sites-doctest-all16-20261018.md`）：

| 结果 | 条数 | 说明 |
|---|---:|---|
| 编译失败 | **8** | 闸门判「不用」但删了编不过——文本启发式的假阳性 |
| 编译通过、收益在噪声内 | **7** | 实测变化 −0.528% ~ +0.298%，远低于聚合噪声线 1% |
| 编译通过且经复测确认省时 | **1** | `prelude.h → <unordered_set>`，−3.008% |

两个数字因此必须同时说：

- **闸门确实提高了「值得动编译器」的比例**：闸门关时 5 条里 0 条能编过，
  闸门开时 16 条里 **8 条**能编过；
- **但闸门远不是保证**：放行的 16 条里 **一半编译不过**。放行 ≠ 能编过，
  真正决定的是 `verify` 的重编译。这条必须写在任何「闸门有用」的说法旁边。

另外 7 条「编译通过但测不出收益」的候选，理论收益并不小（`sstream` 一条
按归因行数是 `1738 × 24 = 41,712 行`，占全项目 0.64%），实测却是 −0.104%。
这再次说明**行数只能筛候选、不能预测时间**，与 §9.6 换成本模型是同一个结论。

采纳率因此有两个口径，对外报哪个都要带上下文：

| 口径 | 结果 | 什么时候用 |
|---|---|---|
| 排序前 5 条（原协议） | 1/5 = 20% | 与 json / zlib 的 0/5 同协议对照 |
| 全部 16 条（本轮补测） | **1/16 = 6%** | 回答「真实采纳率是多少」 |

**1/16 是更保守也更完整的数字**，对外默认用它；1/5 只在做同协议工程间对照时引用。

> **2026-10-19 补充：四轮候选精度专项后，同协议重跑。** 排序算法经历了四轮修订
> （供给者唯一性、副作用检测、集合语义、mention 补边修正——见
> `experiments/candidate-precision-round{1..4}-20261019.md`），在**同一语料快照、
> 同一协议**（闸门内 top-16、交替 min-of-3、噪声线 1%、improved 需复测）下重跑：
>
> | 口径 | 10-18（旧算法） | 10-19（新算法） |
> |---|---|---|
> | 已知真值（`unordered_set`，−3.0% / −2.0%）的排名 | 第 2 | **第 1** |
> | 闸门内候选数 | 16 | 13（5 条假阳性在排序层就被挡掉） |
> | 编译通过率 | 8/16 = 50% | **8/13 = 62%** |
> | 采纳率 | 1/16 = 6% | **1/13 = 8%** |
>
> 同样的收益、更少的无效探测。原始数据
> `experiments/results/g2-sites-doctest-pristine-pristine-r4-20261019.md`
> （注：本节旧实验后语料的 `<unordered_set>` 已按上游 PR 补丁删除，重跑前先
> 还原了原始快照；还原前用打补丁语料跑出的 0/13 是「优化已生效」的预期结果，
> 不是回归）。zlib 同日重跑：`zutil.h → <stdlib.h>`（est 12.2%）在新算法下
> **被闸门直接放行并排第 1**（旧算法要关闸门才找得到），采纳率维持 1/16；
> json 维持 0/16——它的已证实收益（−43.5%）在 TU 层而非头文件 site 层，
> 见 §9.5 的口径说明。

### 9.4 存在真实收益时，找得到吗（注入-召回）

往真实工程注入一条确实多余、确实昂贵的 `#include <regex>`，看工具能否找出来
并实测证实。注入的 include 是人造的，编译与测量不是：

| 注入位置 | 候选排名 | 第一次实测 | 独立第二次 | 结论 |
|---|---:|---|---|---|
| 头文件 `prelude.h`（24 TU） | **1 / 17** | 22044 → 20540 ms，**−6.82%** | 21795 → 20457 ms，**−6.14%** | improved（两遍都过线） |
| TU 源 `data.cpp`（1 TU） | 25 / 61 | 908.3 → 855.9 ms，**−5.77%** | 893.7 → 834.3 ms，**−6.65%** | improved（两遍都过线） |

两次是**独立运行**（各自重新扫描、重新编译、重新测量），不是为了挑好看的数——
两次都过线才写进结论。原始数据在
`experiments/results/g2-recall-doctest-{header,tu}-20261018.json`。

头文件级排第 1，TU 级排第 25——**排序用的是行数模型，它只能筛候选，不能给成本
排序**，这一点与 §8 的结论（ρ 0.68、0.57，中度一致）是自洽的，也是下一步最该
修的地方（真实收益 6.6% 的改动被排到第 25 位）。

### 9.5 另外两个工程：json 0/16、zlib 1/16

同一协议在 nlohmann/json（25 TU，C++）与 zlib（15 TU，C）上重跑。**本节的数字
在 2026-10-18 晚被 §9.9 改写了一次**：早先按「收益前 5 条」采样时两个工程都是
0/5，把候选池扩到全量之后，zlib 出现了一条经复测的优化。

| 工程 | 语言 | TU | 闸门开 | 闸门关 | 能编过 | improved | 采纳率（全量） |
|---|---|---:|---:|---:|---:|---:|---:|
| doctest | C++ | 24 | 16 | 66 | 31 | **1** | **1/16**（闸门内）|
| nlohmann/json | C++ | 25 | 0 | 70 | 9（采样 20 条）| 0 | **0/16** |
| zlib | C | 15 | 0 | 16 | 6 | **1** | **1/16** |

**zlib 的那一条**：`zutil.h` 第 29 行 `#include <stdlib.h>` 删掉，9 个受影响
单元全部编译通过，3314 → 3244 ms（**−2.125%**），按正式协议（`runs=3` +
复测 2 遍）判 improved。而闸门把它拦下了——理由是「该文件使用了 `size`
（由 `malloc.h` 提供）」，`size` 显然是 zlib 自己的变量名/参数名，不是
`<stdlib.h>` 的依赖证据。这是一个**有代价的假阴性**，详见 §9.9。

**json 仍然为 0**：关掉闸门全量 70 条、按收益上限采样前 20 条（覆盖 91% 的
收益上限），9 条能编过，最高的一条是 `serializer.hpp → <iomanip>`，单遍
1.246%，正式复测三遍读数是 **1.98% / −0.18%**，判 no-change——差一点过线，
但复测一致性不够，这个判定是对的。

三个工程放在一起，结论必须改写：

- **1/16 不是「只有 doctest 有」，而是「三个工程里有两个各有 1 条」**；
- **闸门不是安全的默认**：zlib 上它漏掉了一条 2.125% 的改动。它的价值是**降低
  验证成本**（候选砍到 1/4），代价是**可能漏**——两者都是真的，必须一起说；
- zlib 这一组还补了一个语言盲区：此前所有实验都是 C++，zlib 是 C，`-H` /
  `-ftime-trace` 路径与 C++ 不同。工具在 C 上能跑、能出候选、能验证。

### 9.6 排序：从「行数」换成实测成本之后

前面所有排序用的都是归因行数（`行数 × 包含次数`）。它是一个**结构代理**，
不是成本。§9.4 已经露出破绽：注入的那条真实收益 6.8% 的改动，在 TU 级被排到
第 25/61。这次直接换掉排序依据再测一遍。

新排序用 `-ftime-trace` 实测的每个头文件**自身耗时**（必须扣除嵌套子头的
区间，否则「伞头文件」纯因子头多而显贵——与 §8 里还原 CBA 口径是同一个坑）。

doctest、24 TU、同一批 16 条闸门候选下的对照：

| 名次 | 行数模型 | 实测成本模型 |
|---:|---|---|
| 1 | `prelude.h → algorithm`（216,456 行） | `prelude.h → unordered_set`（0.614 s） |
| 2 | `prelude.h → unordered_set`（177,024 行） | `prelude.h → iomanip`（0.475 s） |
| 3 | `prelude.h → vector`（174,096 行） | `prelude.h → vector`（0.372 s） |
| 4 | `prelude.h → set`（152,088 行） | `prelude.h → algorithm`（0.358 s） |
| 5 | `prelude.h → iomanip`（134,832 行） | `prelude.h → set`（0.326 s） |

拿 §9.3 的验证结果对照这两张榜单：

- 行数模型的 **Top-1 是 `algorithm`，删了编译不过**；
- 成本模型的 **Top-1 是 `unordered_set`，正是三条工程里唯一被证实可删且真省时
  的那条**（−3.01%，复测通过）。

量化的那一行是：`algorithm` 的行数比 `unordered_set` **多 22%**，实测成本却
**低 42%**。行数差 22% 的两个候选，成本差 68%——这就是「行数只能筛候选、
不能给成本排序」的直接证据，也是 §8 里 ρ 只有 0.68 的同一个根因。

代价（**这是它默认关闭的唯一理由**）：`-fsyntax-only` 下 clang 会丢弃
`-ftime-trace`（实测 23.1.3 报 `argument unused during compilation`），所以
采集要真编译一遍全项目。实测扫描耗时 31.4 s → 53.7 s，**1.71×**。另外它
是 clang-only；拿不到数据时工具会写 warning 并回退行数，不会假装测过。

### 9.7 白卷不是沉默：0 条候选时工具说了什么

§9.5 里 json 与 zlib 的闸门都是 0 条。这是产品层面最容易误读的一格：
一张空的候选表会被当成「构建没问题」，而真实情况是**每一条都被判过、
都被判了「删了编不过」**。所以这一轮给「交白卷」补了输出：成本集中在哪、
收益最高的那几条为什么被拦、下一步该看什么。

`experiments/g2_diagnosis.py` 在三个工程上跑同一个开关（`--header-sites`）：

| 工程 | TU | 放行 | 拦下 | 项目自有头占解析量 | 前 10 个头占比 | 拦下原因分布 |
|---|---:|---:|---:|---:|---:|---|
| doctest | 24 | 16 | 557 | **1.6%** | 24.2% | 系统头 505 / 真依赖 47 / 无法判定 3 / 单单元 2 |
| nlohmann/json | 25 | 0 | 369 | **18.7%** | 26.2% | 系统头 299 / 真依赖 68 / 无法判定 2 |
| zlib | 15 | 0 | 58 | **41.1%** | **73.4%** | 系统头 40 / 真依赖 16 / 已被别处拉入 2 |

三件事因此变得可核对：

1. **「贵」和「能删」被分开了，而且是量化的**。doctest 收益最高的一条是
   `prelude.h → windows.h`（放大 2,944,992 行，24 个单元都解析），被拦下的
   原因是它真的在用（`NOMINMAX`、`WINAPI_FAMILY`、`__cdecl`）。json 的
   Top-1 是 `adl_serializer.hpp → from_json.hpp`（1,582,925 行），同样被判在
   用（`adl_serializer`、`from_json` 等由 `from_json.hpp` 提供）。成本榜的
   第一名不等于可删的第一名——这正是本工具与「按行数排行榜」类工具的分界。
2. **白卷工程的钱不在自己的头文件里**。doctest 只有 **1.6%**、json **18.7%**
   的解析量落在项目自有头上；zlib 是 **41.1%**，且高度集中（前 10 个占
   **73.4%**，`zlib.h` 一家 23.3%）。前者说明「删 include 行」的收益上限本来
   就很低，后者说明 zlib 的治理方向是拆 `zlib.h` 这个伞头，而不是删行。
   json 的 18.7% 里含 `tests/thirdparty/doctest/doctest.h`（4.2%，vendored
   第三方但物理上在项目内），扣除后自研头占 **14.5%**——口径与 §8 里
   「doctest.h 不算项目头」的告警是同一件事。
3. **闸门有假阴性，而且这次抓到了一例**。zlib 的 `zconf.h → <limits.h>` 被判
   「正在使用」（`UINT_MAX`、`ULONG_MAX`、`USHRT_MAX` 这些宏），所以没进候选；
   但 §9.5 的闸门关对照里，这一条实测**15 个单元全部编译通过**，只是仅省
   0.356%。也就是说闸门保守到了会漏掉真能删的项。这是它的代价，不是优点：
   换来的是「放行的候选里 0 条编译失败」，付出去的是极少数低收益项。

**可以说**：0 条候选时工具给出的是一份可核对的原因清单（每条带标识符或
「在系统头内部」），而不是一张空表。

**不可以说**：「因为成本不在项目头里，所以删 include 没用」——doctest 的
1.6% 是这工具算出来的归因量，它衡量的是**解析行数**，不是墙钟时间；
一个 1.6% 的头也可能占掉 10% 的模板实例化时间，这一点本实验没有测。

复现（依赖 `experiments/_work/` 下已解压的三个工程）：

```bash
python experiments/g2_diagnosis.py --project experiments/_work/json \
    --db experiments/_work/compile_commands.json --tus 25
python experiments/g2_diagnosis.py --project experiments/_work/zlib \
    --db experiments/_work/zlib/compile_commands.json --tus 15 \
    --compiler "C:/Program Files/LLVM/bin/clang.exe"
python experiments/g2_diagnosis.py --project experiments/_work/doctest \
    --db experiments/_work/doctest/compile_commands.json --tus 24
```

产物：`experiments/results/g2-diagnosis-{json,zlib,doctest}-20261018.{json,md}`。

### 9.8 闸门该开多紧：三档探测

§9.3b 暴露出闸门的假阳性有一半。那么反过来——闸门是不是也可能太紧？这一轮
用**只验编译**的档位（`--probe-compile`，每条候选删一次、编一次，不测时间，
成本约为完整测量的 1/6）把三种松紧都过了一遍，所以这次是**全量**而不是 top-5：

| 闸门策略 | 候选 | 编译通过 | 通过率 | 探测耗时 | 每条耗时 |
|---|---:|---:|---:|---:|---:|
| `strict`（默认：只放「疑似未使用」） | 16 | **8** | **50%** | 217 s | 13.6 s |
| `+unknown`（`--allow-unknown-sites`） | 19 | **10** | **53%** | 263 s | 13.8 s |
| `off`（完全不筛，消融对照） | 66 | **31** | **47%** | 810 s | 12.3 s |

数据说明一件与直觉相反的事：**闸门对「能不能编」几乎没有预测力**。放行的
16 条通过率 50%，完全不筛的 66 条是 47%，两者在统计上不可区分（8/16 vs
8/50+，Fisher p ≈ 0.8）。它真正做的事是**把候选砍到 1/4**：verify 成本随之
降到 1/4，代价是能编过的候选从 31 条变成 8 条。

这也推翻了 §9.3 里那句「闸门把 0/5 提到 1/5」的解释：那是**小样本排序效应**，
不是闸门的预测力。§9.3 保留原文作为过程记录，但结论以本节为准。

`--allow-unknown-sites` 的性价比在本次测量里是划算的：多 46 秒探测，多拿到
2 条能编过的候选（10 vs 8），且多出的候选带低可信度标记。

`--probe-compile` 本身也是对「候选表里一半编不过」的产品化回应：报告会把
候选分成「编译探测通过」与「编不过」两类，并明写前者**不等于**省时。

**闸门漏掉收益了吗？**——这是上面那句话必须回答的下一问。闸门关时能编过的
31 条里，有 **23 条不在闸门放行集合内**。把这 23 条按单遍测一遍做初筛：

| 单遍读数区间 | 条数 |
|---|---:|
| ≥ 2%（超过聚合噪声线） | **1** |
| 0.1% – 0.8% | 11 |
| ±0.1% 以内或负数 | 11 |

唯一超过 2% 的那条（`debug_output_window.h → context_state.h`，单遍 3.738%，
只影响 2 个单元）按正式协议复测后是 **−0.548%，no-change**——单遍读数就是噪声。

所以**在这一个工程上**（doctest），答案是：闸门没有漏掉省时的改动。它漏掉的是
「能编过、但删了不影响耗时」的候选，而那些本来也不该被推荐。66 条候选池里经复测
确认省时的只有 1 条，恰好被闸门放行。

**但这个结论不能外推**：同样的实验在 zlib 上得到了反例——闸门漏掉了一条删掉后
省 2.125% 的改动（§9.9）。一个工程的「没漏」不是「不会漏」。

> 顺带又一次验证了复测的必要性：3.738% 的单遍读数复测后变成 −0.548%。如果
> 只看单遍，这条会被当成一个漂亮的优化推荐出去。

复现：`experiments/results/g2-recall-off-doctest-20261018.{json,md}`
（全部 66 条探测 809 s，23 条初筛 1383 s，复测 1 条）。

### 9.9 闸门漏掉了什么：三个工程的召回实验

§9.8 只回答「闸门紧不紧」，没回答「紧得对不对」。这一节关掉闸门、把候选池摊开，
专门找**能编过、但闸门没放行**的候选，看里面有没有值得采纳的。

协议（`experiments/g2_recall_off.py`）：先只验编译找出所有能编过的候选，剔除闸门
放行的那些；对剩下的做**单遍**测量初筛（门槛 2%），过门槛的按正式协议复测
（`runs=3` + 复测 2 遍）。单遍只用来排序，不用来下结论。

| 工程 | 闸门关候选 | 探测采样 | 能编过 | 闸门外能编 | 初筛过 2% | 复测 improved |
|---|---:|---|---:|---:|---:|---:|
| doctest | 66 | 全量 | 31 | 23 | 1 | **0**（复测 −0.548%）|
| nlohmann/json | 70 | 前 20（覆盖收益上限 91%）| 9 | 9 | 0 | **0** |
| zlib | 16 | 全量 | 6 | 6 | 2 | **1**（`zutil.h → <stdlib.h>`，**−2.125%**）|

**zlib 上闸门确实漏了一条。** `zutil.h` 的 `#include <stdlib.h>` 删掉后 9 个
单元全部编译通过，3314 → 3244 ms，复测通过。闸门拦它的理由是「该文件使用了
`size`（由 `malloc.h` 提供）」——`size` 是 zlib 自己的变量名/参数名，不是
`<stdlib.h>` 的依赖证据。文本启发式把**普通词**当成了符号依赖。

**json 仍然 0**：最接近的一条是 `serializer.hpp → <iomanip>`，单遍 1.246%，
正式复测三遍读数是 **1.98% / −0.18%**，判 no-change。差一点过线，但复测不一致
说明它不是稳定收益——这一条同时是「复测机制救了一次误判」的实例。

**顺带修掉一个真缺陷**（`attrib/usage.py::_BUILTIN`）：同一类假阴性的另一半来自
编译器内建——`zutil.h` 那条最初还被 `_MSC_VER`、`__STDC_VERSION__`、
`__attribute__` 判成"在用"，而这三个都不可能因为删掉 `<stdlib.h>` 而消失
（两个是编译器预定义宏，一个是 GCC 扩展关键字）。现在它们不算依赖证据。
修复后 doctest 的候选集不变（仍 16 条），zlib 那条仍被 `size` 挡住——**剩下的
问题是真的，要靠语义判定，不是调词表就能解决**。

产品化：新增 `--ungated-sites`，让用户在验证便宜时关掉闸门换召回。zlib 这种
15 单元的小工程，全量探测只用 29 秒；doctest 的 66 条要 810 秒——**这个开关该不该
开，取决于工程规模，不是取决于我们喜欢哪个结论**。

### 9.10 判定

| 子问题 | 判定 | 关键数字 |
|---|---|---|
| G2-1 可行性闸门有效 | **成立（有限），且已知会漏** | 作用：候选砍到 1/4（verify 成本 1/4）；局限：**对「能不能编」无预测力**（50% vs 47%，§9.8），**且会漏收益**——zlib 上漏掉一条实省 2.125% 的改动，根因是 `size` 这类普通词被当成依赖证据（§9.9） |
| G2-2 天然候选的可采纳率 | **成立（有限），三个工程里两个各有一条** | 全量口径：doctest **1/16**（−3.01%）、zlib **1/16**（−2.125%）、json **0/16**；前 5 条采样口径下是 1/5、0/5、0/5——采样会漏 |
| G2-3 有真实收益时的召回 | **成立** | 头文件级 1/17、TU 级 25/61，两者均被实测证实 |
| G2-4 排序用实测成本优于行数 | **成立（单工程）** | doctest 上 Top-1 由「删了编译不过」换成「唯一可采纳的那条」 |
| G2-5 白卷可解释 | **成立** | json 369 条 / zlib 58 条逐条给出拦下原因与标识符证据；成本集中度可量化 |

**可以说**：在三个真实工程里，工具找到并证实过 **2 条**优化——doctest 删
`prelude.h` 里的 `<unordered_set>`（24 单元全通过、聚合 −3.01%、复测通过，
实测成本排序下排第 1）；zlib 删 `zutil.h` 里的 `<stdlib.h>`（9 单元全通过、
3314 → 3244 ms、−2.125%、复测通过）。

**不可以说**：

- 「自动优化」或「帮你找到优化」——三个工程各只有 **0–1 条**（1/16、1/16、
  0/16），而且这两条里有 1 条是**关掉闸门才找到**的（zlib），不是默认配置的产出；
- 「这条改动对 doctest 的用户也安全」——验证只覆盖了编译数据库里的 24 个
  单元，没有覆盖 doctest 的下游使用者，也没有覆盖 `prelude.h` 里那些按平台
  分支的条件编译路径；
- 「换成本排序就能找到优化」——G2-4 只在 doctest 一个工程上测过，它的证据是
  **排序变好了**，不是**命中率变高了**（候选集没变，1/5 还是 1/5）；
- 「闸门放行的都能编过」——doctest 上放行 16 条，**8 条编译失败**（§9.3b）。
  更不能说「闸门提高了通过率」：它放行的 16 条通过率 50%，完全不筛的 66 条
  是 47%，统计上不可区分（§9.8）。闸门省的是**候选数量**，不是每条的质量；
- 「闸门不会漏掉可删项」——**这条已经被实测推翻**：zlib 上闸门把
  `zutil.h → <stdlib.h>` 判成「在用」（证据是 `size` 这个词），而它删掉后省
  2.125% 且复测通过（§9.9）。准确的说法是「闸门把验证成本降到 1/4，代价是可能
  漏；小工程可以用 `--ungated-sites` 关掉它换召回」；

### 9.11 失败原因分类与核心指标（2026-10-19 第五轮）

上面所有章节回答「候选准不准、排得好不好」。还有一个更尖锐的问题没有回答：
**「16 个候选里只有 1 个值得采纳，使用者为什么不直接人工检查？」** 本轮不动
判定规则，只做两件事：把每条候选的失败原因分类，并建立核心指标——
**每投入多少分析时间，产出多少条经复测的有效优化**。

**协议**（`experiments/failure_taxonomy.py`）：扫描与探测全部计墙钟；探测集 =
全部「疑似未使用」+ 全部「无法判定」+ 预估收益前 40 条的 in_use **镜像样本**
——只探测推送集量不出「保守漏报」，必须把被判「在用」的也测一遍。三条真值
不变：编译、解析量差、汇编指纹；有计时实测的语料再按噪声线分档。

| 工程 | TU | 候选 | 疑似未使用 | **已证实** | 保守漏报 | 每 100 TU | 分析分钟 | 分钟/条 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| doctest | 24 | 38 | 3 | 3 | 1 | 12.5 | 0.51 | 0.17 |
| zlib | 34 | 40 | 1 | 1 | 0 | 2.9 | 0.14 | 0.14 |
| Lua 5.4.7 | 34 | 222 | 20 | 19 | 45 | 55.9 | 0.59 | 0.03 |
| spdlog | 8 | 26 | 2 | 0 | 1 | 0 | 0.50 | — |
| **合计** | **100** | — | — | **23** | **47** | **23.0** | **1.7** | **0.08** |

三个问题的回答：

- **为什么不人工检查？** 因为人工检查就是工具已经做了的事：镜像样本显示
  gated 候选里绝大多数（doctest 31/35、zlib 37/38）在 usage 层就被符号级
  证据**正确拦下**，根本不值得编译。工具把 N 次「改一行 → 编一次 → 看报错」
  压到个位数；对剩下极少数候选，它还提供人工不会做的第三轴（汇编指纹）。
- **收益能抵消验证成本吗？** 合计 **1.7 分钟分析产出 23 条**已证实候选，
  约 **4.5 秒/条**；计时层过噪声线的两条（doctest −2.0%、zlib −2.7%）单条
  收益都是聚合百分数级。解析层证实的边际成本极低，计时层贵（交替 min-of-3
  + 复测）——所以计时只花在预估收益足够大的候选上。
- **零假阳性是准确还是保守？** 两者都有且可分开量化：**推送集零假阳性是
  准确**（26 条疑似未使用里只有 1 条判定漏判，且是已知 AST 边界）；
  **保守是真实存在的**——四语料镜像共 47 条漏报，集中在两个点：副作用启发式
  在 UCRT/MSVC 宏上误判（Lua 13 条）、unknown 层一律不推（Lua 32 条，设计
  如此）。规模上 47 条里只有 1 条预估超过 0.1 s——**保守挡住的主要是小额
  机会，放宽规则换来的主要是噪音**。

**本轮修掉一个真实工具 bug**：给 spdlog 自建 compile_commands.json（相对
`-Iinclude`）后整个语料判定集体退化——疑似未使用从 2 条虚增到 7 条。根因是
`-H` 打印的路径形态跟着编译 cwd 走，而下游按扫描进程 cwd 解析：头文件
「存在但读不到」，行数记 0、标识符集为空，**用法判定静默退化且不报错**。
修复在 `GccLikeDriver.run`（唯一知道编译 cwd 的地方）：事件解析后把相对
路径就地落地。两条回归测试锁住（`tests/test_drivers.py`）。

**案例：计时口径的最大「赢家」是一次静默改程序**（详见
`experiments/candidate-precision-round5-20261019.md`）。spdlog 语料上
`cfg.cpp → helpers-inl.h` 测出 **−77.8%（四次独立运行复现）**，是全部语料
最大的单条计时收益，usage 判定 in_use。本轮补第三轴：删除后汇编从
**10,329 行塌缩到 40 行**——cfg.cpp 就是把
`spdlog::cfg::helpers::load_levels` 等函数编进库的 TU，删掉的是它们的
**定义**。`-fsyntax-only` 照样过（声明在别的头里），计时测到的「省时」是
真的，产物少了整个公共 API 的实现，链接期才炸。同一语料的
`async.cpp → async.h`（+2.4~2.9%）同样是静默改程序。**计时单独庆祝的两条，
在第三条真值下全部现形**——这不是计时测错了，是计时回答不了「程序还是不是
同一个」；反事实实验必须三轴齐上，而人工评审默认不会做第三轴。

## 10. G3：门禁成立（2026-10-18）

### 10.1 场景与协议

样本为 `benchmarks/cases/demo` 的副本（原工程不被修改），每场景重复 3 次：

1. **无回归**：树不变，门禁必须通过——误报比漏报更能毁掉一个门禁；
2. **注入回归**：新建一个 22,903 行的头并让 `main.cpp` 包含它（约 +10% 归因行数）；
3. **构建损坏**：给 `util.cpp` 追加一行非法 C++，使其编译失败。

### 10.2 结果

| 场景 | 结果 |
|---|---|
| 无回归 | 通过 **3/3**，误报 0 |
| 注入回归 | 检出 **3/3**（报出 +10.0% 并列出最差头文件） |
| 构建损坏 | 检出 **3/3** |
| 单次门禁耗时 | 中位 **3.38 s**（同规模一次普通扫描的同量级） |

### 10.3 本轮修掉的严重缺陷：越坏越绿

第一版注入时 `main.cpp` 编译失败，TU 从 2 掉到 1，总成本算出 **−67.7%**，
门禁**通过**了。原因：门禁只比较总量，而少一个单元会让总量「下降」。
构建坏得越彻底，越容易被判成大幅改善——这与门禁的目的完全相反。

已修为：只要可用单元数少于基线，门禁**直接失败**并给出原因
（「comparison is incomplete … if files were removed on purpose, update the baseline」）。
两条把旧行为当期望的测试也已改写。

### 10.3b 真实工程复测（nlohmann/json，25 个 TU / 4,491,172 行）

构造样本只有 2 个 TU，单靠它支撑门禁太薄。在真实工程上重复同样三个场景
（`experiments/g3_real.py`）：

| 场景 | 期望 | 结果 | 单次耗时 |
|---|---|---|---:|
| 无回归（3 次） | 通过 | **3/3** | 30.3 s |
| 注入回归（+10%，449,117 行） | 失败 | **3/3** | 39.6 s |
| 构建损坏（一个 TU 编译失败） | 失败 | **3/3** | 29.9 s |

注入回归时门禁报出的就是实测变化：「头文件解析量：4,491,172 → 4,940,290 (+10.0%)」，
并列出最差头文件；构建损坏时成本反而「下降 4.0%」，门禁仍判失败——这正是 §10.3
修掉的那条路径在真实工程上的复验。

**实验装置上犯过一次错，记在这里以免重演**：第一次把注入目标写成固定的
`tests/src/unit-algorithms.cpp`，三次注入全部 `+0.0%`——那个文件不在 `--max-tus 25`
的扫描集合里，改了等于没改。看起来像「门禁漏报」，实际是仪器指错了文件。
现在注入目标从基线扫描的实际单元里取，并在输出里打印它。

### 10.4 判定

| 门槛 | 判定 | 依据 |
|---|---|---|
| G3 治理成立 | **成立（限归因行数型回归）** | 构造样本与真实工程（25 TU）均：检出 3/3、误报 0 |
| 已知盲区 | **行数不变但编译变慢的回归测不出** | 例如宏展开变复杂、模板实例化变重 |

盲区必须写进任何对外材料：门禁挡的是「头文件覆盖面膨胀」，不是「构建变慢」的全部。

## 11. G4：工程开销成立（2026-10-18）

### 11.1 协议

同一工程（25 个 TU）、`--jobs 1`、重复 3 次取中位。
「纯编译时间」来自扫描自己记录的每单元墙钟（`baseline_seconds`），
开销倍数 = 扫描墙钟 ÷ 纯编译墙钟。

### 11.2 结果

| 编译器 | 扫描墙钟 | 纯编译 | 开销倍数 | 分析独占 | 峰值内存 | 归因行数一致 | Top-10 一致 |
|---|---:|---:|---:|---:|---:|---|---|
| g++ | 41.6 s | 36.16 s | **1.15×** | 5.44 s | 9.2 MB | 是 | 是 |
| clang++ | 33.93 s | 28.30 s | **1.20×** | 5.63 s | 9.2 MB | 是 | 是 |

### 11.3 判定

| 门槛 | 判定 | 依据 |
|---|---|---|
| G4 工程开销 | **成立** | 开销 ≤1.2×、峰值 9.2 MB、两编译器确定 |
| MSVC | **已解除（CI 实测）** | 本地 `vcvars64` 依赖被策略拦截的 `reg.exe`，改由 CI 的 windows-latest 执行：`scan --compiler cl` 得到 **TU=2、失败 0、归因行数 196,157**，随后 `gate` 无回归通过。run #5 与 #6 均 success，产物 `msvc-evidence` 可下载 |

口径必须带着：峰值内存是**扫描主进程**的工作集，**不含编译器子进程**；
开销倍数含解释器启动，在几十个单元的小工程上这部分不可忽略。

**跨编译器的可比性（MSVC 证据顺带暴露）**：同一个 `benchmarks/cases/demo`，
GCC 归因 228,987 行、MSVC 归因 196,157 行，差约 14%。原因不是其中一个算错，而是
两边**包含的系统头不同**（MSVC 的 CRT 头与 libstdc++ 是两套）。因此：

- 归因行数**只能在同一编译器内做纵向比较**（基线 vs 新代码）；
- 跨编译器的数字**不可直接相减**，报告里凡涉及跨工具链都要写明这一点。
