# PCH 实测闭环：nlohmann/json 单元测试（2026-10-25）

把 `scan --pch` 的**估算**拿去**真的做一遍**：生成 `.gch`、逐单元双侧重编、计时。
要回答一个问题——估算说的「覆盖率」在实际构建里能兑现多少。

- 语料：nlohmann/json v3.11.3（`experiments/fetch.py` 固定），72 个 `tests/src` 单元
- 编译器：g++ (MinGW x86_64-win32-seh-rev1) 16.2.0
- 口径：`-fsyntax-only`（不含代码生成），每侧编译 2 次取最快，进程墙钟
- 复现：`python experiments/pch_verify_json.py --units 24 --runs 2`

## 结果

| 指标 | 数值 |
|---|---|
| 估算覆盖率（上界） | 86%（56/57 个单元包含这些头） |
| **实测采用率（下界）** | **62%（15/24 个单元编译器真的用了 .gch）** |
| 全项目口径 | 26%（15 个 / 全项目 57 个单元） |
| 采用口径节省 | **53.1%**（14.4 s → 6.7 s） |
| 全组口径节省 | 46.4%（含 9 个用不上 PCH 的单元） |
| 生成 .gch 一次性开销 | 1.57 s |
| 回本所需单元数 | 2 个 |

三次独立运行（两次由 `pch_verify_json.py` 产出 md 与 json，一次手工）：采用口径
53.5% / 53.1% / 52.9%，全组口径 47.3% / 46.4% / 47.0%——**两次运行之间差约 0.9 个
百分点**，这个量级是本机噪声，比它更小的差异不作结论。

## 三个只在实测里才看得见的东西

### 1. 估算的 86% 是一个上界，实际能用的只有 62%

估算按「包含这些头的单元」计数。它看不见的是：一份 `.gch` 只在**编译选项完全
相同**的单元间共享，也看不见某些单元加上 PCH 之后根本编不过。实测把这两层都
量出来了。

### 2. 24 个单元里 9 个加了 PCH 后编不过

这是本轮最有价值的发现。失败的单元报的是宏状态被 PCH 固化后的类型错误，例如：

```
tests/src/unit-class_lexer.cpp:18:1: error: 'using json::lexer = class ...'
```

原因与 2026-10-17 那次完整构建实验里踩到的是同一个（当时是「断言数变了」，门禁
抓到后改成「凡在 include 之前改配置宏的单元一律不用 PCH」，16/63）：**在 include
之前改配置宏的单元，其宏状态会被固化进 .gch**。那次的处置是人工排除；这次是由
工具自己量出来并逐单元列出。

关键区别：那次是通过「跑测试看断言数」发现的，`-fsyntax-only` 看不到；这次
`pch-verify` 只编译就抓到了——因为它编译失败，而失败是编译期就能观察的。

### 3. 「省了 500 ms」有可能是编译提前失败造成的

9 个失败单元的耗时都比基线短 460–530 ms——它们不是变快了，是**提前退出了**。
第一版报告把这一列如实写成 `-495 ms`，读者会读成「PCH 让它快了 500 ms」。已改成
失败单元显示「编译失败 / —」，不给出变化量。

同理，收益分两个口径报：

- **采用口径 53.1%**：只算编译器真的用了 `.gch` 的 15 个单元——这是 PCH 本身的功劳。
- **全组口径 46.4%**：`-include` 加上去之后总耗时的变化，含那 9 个失败单元。

只报前者会掩盖「37% 的单元用不了」；只报后者会把失败造成的提前退出算成收益。

## 修正的两个实现缺陷（都是这次实测抓出来的）

1. **采用判定的正则误报。** 第一版用 `(?:gch|pch)\b[^\n]{0,200}?(?:not used|
   ignored|invalid|…)`。json 的 `unit-allocator.cpp` 的 stderr 里有
   `In file included from …heavyheader_pch.h:2:` 这样的诊断上下文行——`pch` 被当成
   `.gch`，后面 200 字符内出现一条**无关**的 `invalid use of …` 就判「未采用」。
   12 个单元里错 1 个，而那个单元明明省了 486 ms。改成要求「拒绝原因紧跟在
   `.gch` 之后」，并加了回归测试。

2. **「没有输出」曾被判成未采用。** `-Winvalid-pch` 只在**拒绝**时开口，采用成功
   时一句话都不说。把它判成 False 会把每一次成功的实测都记成失败——错误方向是
   「数字变难看」，不会有人来报，是单元测试抓出来的。

## 局限

- **只测了一组编译选项指纹**（`ec6f9dbf1199`，56 个单元）里的 24 个。同一份 `.gch`
  无法跨指纹共享，所以 53.1% 不能外推到全项目 57 个单元。
- **`-fsyntax-only` 口径**，不含代码生成与优化，数值高于完整构建的收益。历史归档
  里完整构建是 −11.4%（那次还人工排除了 16 个配置宏单元）。两者不是同一把尺子。
- **不检测语义变化。** 编译通过 ≠ 程序行为一致。2026-10-17 那次是靠跑测试、比对
  断言数发现的；本模块只做编译期判定，不做运行期校验。
- **没有做行数↔秒的换算**，因此不报「预测误差」。不存在诚实的换算系数（用预处理
  占比推算实测收益会高估约 1.6 倍，见 `pch-greedy-selection-20261024.md`）。
- **语料布局有讲究**：不能拿 `tests/src` 当扫描根，那样 `include/nlohmann/json.hpp`
  会被判成外部头，一个候选都选不出来。`pch_verify_json.py` 负责摆成同一个根。
- **并行度**：这 72 个单元每个都要实例化 doctest + json.hpp 的完整模板体，默认
  `-j`（= CPU 核数）会把内存吃满开始换页。脚本默认 `-j 4`。

## 追加：把「9 个编不过」变成静态可算的预警（2026-10-26）

上一节量出 24 个单元里 9 个加 PCH 后编不过。这 9 个长什么样？看源文件第一屏就
看出来了——它们都在 `#include <nlohmann/json.hpp>` **之前**写了
`#define JSON_TESTS_PRIVATE`：

```cpp
#include "doctest_compatibility.h"   // 第一个候选头，它前面没有宏
#define JSON_TESTS_PRIVATE          // ← 风险在这里
#include <nlohmann/json.hpp>        // 第二个候选头
```

机制：`-include` 把 PCH 插到每个单元最前面，头文件看到的是「它原本的 include
位置之前」那套宏状态。`JSON_TESTS_PRIVATE` 打开私有成员访问、改变类定义，而 PCH
已经用「宏没定义」的状态把它编译过一次了——于是类型对不上。

于是把这条做成静态预警（`attrib/pch.py: macro_prefixed_units`）：读源文件，找
「任一候选头的 include 之前」的第一条 `#define`/`#undef`。不需要编译。

**它的准确率由实测打分，不由我们声明**（同一批 24 个单元）：

| | 加 PCH 后编不过 | 加 PCH 后编得过 |
|---|---:|---:|
| **有预置宏**（预警） | 9 | 1 |
| 无预置宏 | 0 | 14 |

- **召回 100%**：所有编不过的 9 个都在预警名单里。
- **精确 90%**：预警的 10 个里 9 个真的编不过，虚报 1 个。

虚报的那个是 `unit-assert_macro.cpp`，它 `#define JSON_ASSERT(x) {...}`——改的是
断言宏，不改变类定义，所以编得过（行为仍然可能不同，那要靠运行期校验，本工具不做）。
这正好划出这个预警的边界：**它能判断「宏状态会被固化」，不能判断「固化后会不会炸」**。
所以报告的措辞是「风险清单，不是失败预言」。

召回比精确重要的理由：漏报会让一个单元在「看起来成功了」的情况下改变语义，虚报
只是让人多检查一个单元。

顺带修了一个只有多候选头时才暴露的 bug：第一版在遇到**第一个**候选头（
`doctest_compatibility.h`）时就返回，那时前缀还是空的，于是 json 上一条预警都
报不出来。PCH 里往往不止一个头，必须查完所有候选头的 include 位置。

复现：`python experiments/pch_verify_json.py --units 24 --runs 2`，报告末尾的
「静态预警与实测的对照」一节由工具自己生成。
